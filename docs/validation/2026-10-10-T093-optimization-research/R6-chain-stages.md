**一句话结论**：现行顺序 Balance → Clay → Color → Limit → 末端站得住（Clay 挪到最前没有可测收益），不缺「新模块」，缺的是三件小事：两个倾斜各对一个参考、互相打架；流媒体 / 俱乐部档对热混音没有「往下」的增益路径，流媒体版反而被多压；自动 Heat 底量按公式算可能听不见。三件都是零延迟、零 CPU，代价 S～M。

## 1. 现行顺序的逐级论证

### 1.1 每一级为什么在这里、换位置会怎样

| 级 | 为什么在这里（本项目理由 + 公开原则） | 换位置会怎样 |
|---|---|---|
| 入口测点（IN 表、分析器、Balance 分析帧） | 画像只取原始输入，不随 GLAZE 变（ADR-008、ADR-009 决定 2；`CeladonChain.cpp:435-446`） | 挪到任何模块之后都会变成「按自己的输出决策」的闭环 |
| Balance 第一 | 先做修正，后做美化；线性修正先于非线性处理。iZotope 官方博客原话：「9 times out of 10 … linear corrections before non-linear ones」【一手，iZotope Learn】；Ozone 8 默认顺序 EQ → Dynamics → Maximizer【一手，Ozone 8 文档】；MIT 21M.380 讲义转引 Katz 2014a p.131：母带里 EQ → 压缩更常见【统计】 | 放到 Color 之后，它分析到的是加过谐波、压过的谱，修正会跟着 Heat / Glue 抖（源码注释 `CeladonChain.cpp:440-443`）；放到 Limit 之后会把限过的峰再抬起来、破坏 Ceiling |
| Clay 第二 | 超低频清理要早于一切非线性 / 动态级；讲义转引 Ariza：「DC offset removal: high-pass at < 20 Hz」属于 EQ 段【统计】。又要在 Balance 之后，画像才不看到 Clay 自己的结果（ADR-009 备选一） | 见 1.2：挪到最前，音频路径几乎没差别，只换来 Balance 分析的一点泄漏改善，却要另做一套分析或破坏 ADR-008；挪到 Color 之后，Glue / Heat 不受影响（它们的检测本来就过 100 / 150 Hz 高通），只有 Clip 和限幅器多吃次声 |
| Color 第三（Tone → Glue → Heat → Mix） | 美化在修正之后、限幅之前（iZotope 同文：corrective before sweetening【一手】）。The God Particle 自带限幅，官方说它「meant to sit at the front of your mix bus」（MusicTech 报道 Cradle 原话）【统计】，它是总线一体机，与 Celadon 拆开的「染色段」不可直接比位置 | Heat 在 Glue 之后与讲义转引的「excite early」相反【统计】，但 Heat 残差比例 ≤ 0.25 h（`ColorModule.cpp:90-94`），底量下谐波 −56 dB 以下（见 R6-03），先后几乎听不出差别，不值得换 |
| Limit 第四 | 所有来源一致：限幅最后（Ozone 默认、讲义「Put late in the signal chain」）；ADR-004 检测在 8× 域、增益在 1× 域 | 任何放在它后面的处理都可能破坏真峰值保证 |
| 末端（OUT 表 → GLAZE 出口 → Listen → 差值 → 预听 + 抖动） | 测点读母带，监听增益不进测量（`CeladonChain.cpp:467-508`）；讲义转引 Katz「requantize last」【统计】 | 抖动必须最后；监听若放在测点之前，表和 GLAZE 会把监听增益当成母带 |

### 1.2 ① Clay 低切：放 Balance 之后（现状） vs 放最前

| 影响面 | 定量（48 kHz，House 自动低切 25 Hz，4 阶 Butterworth） | 结论 |
|---|---|---|
| Balance 的音频路径 | 最低段峰值滤波器中心 39.37 Hz、Q 4.318：+6 dB 时对 20 / 25 / 30 Hz 只抬 +0.16 / +0.37 / +0.94 dB；−8 dB 时 −0.22 / −0.51 / −1.30 dB（估算） | 两种顺序下，Balance 对次声的作用都在 1 dB 以内。Clay 在后，还能把 Balance 抬出来的次声切掉 |
| Clay 对 Balance 频段 | 25 Hz 低切在 40 / 50 / 63 Hz 只衰减 −0.10 / −0.02 / 0.00 dB（估算） | ADR-009 说的「几乎等效」在音频路径上成立 |
| Balance 的分析（GLAZE 画像也读它） | 48 kHz / 2048 点下 bin 宽 23.4 Hz。按段边界重叠计权（`BalanceModule.cpp:316-343`），「40 Hz 段」几乎只取 46.9 Hz 那一个 bin；Hann 主瓣把 20 Hz、25 Hz 的内容以 −8.0 / −5.2 dB 计入这个 bin（估算） | 这是唯一真实的差别：次声会抬高最低段的读数。但这是 Balance 低段分辨率的问题（T-032 R2-04 低段长窗、R7 低频分辨率都在待拍板），不是挪 Clay 的理由 |
| Glue / Heat 检测 | Glue 侧链先过 100 Hz 高通，分频检测器也在它之后（`ColorModule.cpp:56`、`:67-79`）；Heat 非线性支路先过 150 Hz 高通（`:88-96`） | 把 Clay 挪到最前，对 Glue / Heat 的收益是 0 |
| Clip / 限幅器 | 现在已经在 Clay 之后 | 无差别 |

**结论**：不挪。挪到最前要么另做一套时域分析，要么让画像随 GLAZE 变（违反 ADR-008），换来的只是最低一两段的分析泄漏改善。这一点应交给 R2-04 的低段方案去解决（见「范围外发现」2）。

### 1.3 ② 冗余：三个倾斜、两个非线性、三条响度闭环

| 组 | 现状 | 判断 |
|---|---|---|
| 三个倾斜 | Brighten：只手动，在 Balance 滤波器里做，每十倍频程 3 dB × Brighten/100。Tone：自动，100 Hz / 8 kHz 跷跷板，参考斜率 House −2.25 dB/oct、死区 0.35、往亮封顶 +0.4 dB（`GlazePlanner.cpp:1838-1844`、`GlazeConstants.h:96-97`）。目标频谱：新实例默认「自动」35 % × GLAZE，House 斜率 Deep −1.5 / Tech −0.75 / Melodic −1.25（`CeladonChain.cpp:33-43`），在 Balance 里逐段修正（`BalanceModule.cpp:1763-1824`） | **Tone 和目标频谱用同一种口径（1/3 倍频程段功率，粉噪 = 0），参考却不同**：Tone 的 −2.25 是 45 首标定的中位数，目标频谱的斜率还是没试听过的起点值。结果是目标频谱在默认路径上把几乎每首 House 都往亮推，有时还和 Tone 方向相反，并绕过了 Max 定的 House 往亮上限 → **R6-01**。Brighten 是手动参数，合并会改参数语义，不动 |
| 两个非线性 | Heat：并联残差染色，换算表里对响度、峰值的影响都在千分之一 dB 量级（`GlazeConstants.h:297-311`）。Clip：管峰值的主力，温润 / 冲击风格在超限 4 dB 时给到 71～79（T-032 R6 实验 A） | 两者分工互补，不冗余。共用一个过采样域只省一次上下采样（约 60 样本），却要把 Color 和 Limit 绑在一起，T-047 3c（只对残差做 ADAA）做完后这点收益更小，不做。真正的问题是 Heat 底量听不听得见 → **R6-03** |
| 三条响度闭环 | Listen（整链等响，只衰减，监听用）；归一化预听（到目标 LUFS，只衰减，监听用）；G_trim（输出侧主段电平闭环，进母带） | G_trim 改的是母带，另外两条只改监听，分工不同。Listen 和预听都是「监听增益」，却各有一套平滑器和交接代码（`CeladonChain.cpp:305-336`、`ReleaseSafety`），离线时只关了预听、没关 Listen → **R6-04** |

## 2. 提案（按价值排序）

### R6-01 目标频谱「自动」与 Tone 用同一个斜率参考

- **问题 / 现状**：House 档开着「目标频谱 = 自动」（新实例默认，`ParameterDefaults.h:70-71`）时，链按子类取斜率 −1.5 / −0.75 / −1.25（`CeladonChain.cpp:33-43`、`:244-252`）；Tone 的参考斜率却是标定后的 −2.25（`GlazeConstants.h:96`，T-038 标定：Deep / Tech / Melodic 中位数 −2.21 / −2.19 / −2.24，四分位见 `2026-10-01-T038-calibration/REPORT.md:38-41`）。两者都是段功率口径（`BalanceModule.cpp:1767-1768` 与 `LiveProfile.cpp:2242-2263`）。估算（23 段等权、κ = 1，取上界）：

| 子类 · GLAZE | 曲子斜率（四分位低 / 中位 / 高） | 目标频谱在 12.5 kHz 的修正 | Tone |
|---|---|---|---|
| Tech · 100 % | −2.76 / −2.19 / −1.62 | +0.78 / +0.52 / +0.27 dB（63 Hz 对称往下） | +0.08 / 0 / **−0.14** dB |
| Deep · 100 % | −2.70 / −2.21 / −1.64 | +0.42 / +0.20 / 0 dB | +0.05 / 0 / −0.13 dB |
| Melodic · 100 % | −2.41 / −2.24 / −1.92 | +0.40 / +0.32 / +0.18 dB | 0 / 0 / 0 dB |
| Tech · 35 %（默认） | 同上 | +0.27 / +0.18 / +0.09 dB | 0 左右 |

  这张表说明三件事：Tech 的 15 首里连最亮的四分位都会被往亮推；偏亮的曲子上 Tone 往暗、目标频谱往亮，两者方向相反；而规格专门给 House 的 Tone 往亮封顶 +0.4 dB，理由是「DJ 变速后，靠极高频撑起来的声音会发假」（`设计规格-曲风与交付.md:33`），目标频谱在 12.5 kHz 能给到 +0.78 dB，绕开了这个上限。
- **提案**：二选一，推荐 A。
  - A（单一真源）：「自动」形状的斜率直接取该曲风 / 风格混合后的 `toneReferenceSlopeDbPerOct`（House 全是 −2.25）。目标频谱只修正偏离回归线超过 1 dB 的局部形状，整体倾斜只由 Tone 负责，Tone 的往亮上限照常生效。
  - B（去斜率）：目标频谱的逐段误差先去掉最小二乘斜率分量，只保留形状。「参考」模式（侧链学到的 27 段）也走这一步，参考曲的明暗交给 Tone。
  - 两种做法都只改「自动 / 显式斜率」路径；手动形状与 Brighten 不动。
- **依据**：源码与标定数据如上【一手：本仓库】；冲突量是按 `BalanceModule.cpp:1814-1824`（死区 1 dB、× 0.35、封顶 ±2.5、× 强度）与 `GlazePlanner.cpp:1838-1844` 复算的【推断】。Tonal Balance Control 一类「从参考曲建目标」的思路已经被 T-038 用来定 Tone 的参考（规格第 3.2 节），目标频谱没跟上【推断】。
- **对硬约束与 ADR 的影响**：GLAZE 0 时目标频谱的自动强度为 0，逐位不变。旧工程读入时四项高级处理一律关（ADR-020 决定 3），旧工程也不变。只有新实例在 House / 通用档 + GLAZE > 0 时声音变。这条深化 ADR-020「待 Max 复核」第 2 条（自动目标怎么选形状），不冲突。零延迟、零 CPU。
- **代价与风险**：S（A 改一个映射函数并回写实际参数 `targetSlopeResolved*`；B 在 Balance 每 hop 多一次 23 点回归）。风险：目标频谱在 House 上的作用会变得很小，等于默认路径少一处「往亮」，需要 Max 试听确认不会「变闷」。
- **怎么验**：在 DGX / 109 上跑 `celadon_render`，用 45 首 Jamendo House × GLAZE 35 / 100 × 三子类，改前改后对比 Balance 目标修正量（`publishedTargetDb`）与 Tone 实际值的逐首相关：改后两者同号或其中一方为 0 的比例应接近 100 %；12.5 kHz 净提升不超过 +0.4 dB。22 首门槛 `gate_check.py` 通过；GLAZE 0 逐位直通、块长 {1, 7, 32, 64, 480, 512, 4096} 逐位一致。最后交 Max 做等响 A/B。
- **对 Max 口味的核对**：符合「House 往亮要克制」（他定的 +0.4 dB 上限）和「全自动但每一步可解释」；不碰收单和加宽。

### R6-02 流媒体 / 俱乐部档给 GLAZE 一条「往下」的增益路径

- **问题 / 现状**：GLAZE 只推不减。规划器的请求经过 `nonNegative` 处理（`GlazePlanner.cpp:1700-1712`，注释写明「比目标更响的歌不衰减——没有 cut 路径」）；编排器把有效 Limit Gain 钳在 [0, 24]，守护族最多只收回自动加上去的那部分（`GlazeController.cpp:838-866`）；模块本身也钳在 0～24 dB（`LimiterModule.cpp:110`）。热混音进流媒体档后，有效 Ceiling 降到 −2 dBTP，结果是被多限幅，而不是被调轻。T-085 的渲染数据（GLAZE 100、流媒体）：

| 曲 | 输入 LUFS | 目标 −10 → 输出 / 限幅 GR 均值 / 最大 | 目标 −14 → 输出 / GR 均值 / 最大 |
|---|---|---|---|
| melodic_241941 | −8.50 | −9.66 / 1.92 / 7.58 dB | −9.75 / 1.68 / 5.92 dB |
| deep_155923 | −9.34 | −9.43 / 1.81 / 5.59 dB | −9.73 / 1.44 / 5.49 dB |
| melodic_647576 | −9.90 | −9.24 / 2.03 / 6.41 dB | −10.28 / 0.61 / 5.40 dB |
| stress_hot_mix | −8.00 | −8.68 | −8.68 |

  9 首真歌里有 4 首输入就比 −10.5 LUFS 响。−14 组的输出离目标差 4～5 LU，限幅平均还在压 0.6～1.7 dB。T-085 的报告把「−14 组实测中位仍是 −12.01」归因于「预算 / 守护限制」，这批数据显示，热输入没有往下的路径是另一大原因。Max 的两版交付共用同一份混音，混音越响，流媒体版越吃亏。
- **提案**：流媒体 / 俱乐部档里，当主段输入响度 I 高于交付目标 L_t 时，Limit Gain 的自动部分可以为负：ΔG = −min(X, I − L_t)，X 建议 6 dB。实现上把模块内部的 Gain 下限从 0 放到 −X（参数旋钮仍是 0～24，参数 ID 与范围都不改），编排器的钳位与守护收回量也按同一下限改。标准档维持「已够响仍温和推响」（Max 已定）。另有一个更小的备选：用 Color Output（−6～+6 dB，规划器已经读它，`GlazePlanner.cpp:1583`）承载自动衰减，但它在 Glue / Heat 之后，会让 Color 旋钮的显示变复杂，所以不推荐。
- **依据**：上表来自 `docs/validation/2026-10-08-T085-codec-tp/render_target_-10.csv` / `-14.csv`【一手：本仓库实测】；Spotify 官方：响于 −14 LUFS 时会被调轻，并建议真峰值低于 −2 dBTP（T-085 报告引用的 support.spotify.com 页面）【一手】；「多压换不来更响」是 T-038 / T-047 的共识【推断】。
- **对硬约束与 ADR 的影响**：GLAZE 0 时有效参数等于手动值（≥ 0），逐位不变。旧工程只有在「GLAZE > 0 + 流媒体 / 俱乐部 + 输入比目标响」时声音变，变化方向是限幅更少。它会推翻一条隐含原则：「GLAZE 只加不减」，以及 `testManualComesFirst` 的「手动增益是地板」，**需要 Max 拍板**（见待拍板 1）。零延迟、零 CPU。试听差值的公式（除以 Gain）在 Gain < 1 时仍然成立。
- **代价与风险**：S～M（规划器一处 `nonNegative`、编排器两处钳位、模块下限，外加状态行文案「本曲比交付目标响，已调轻 x dB」）。风险有两点：输入本身已经压得很扁时，调轻不能恢复动态（PSR 不会变好），只是不再多压；俱乐部档 −7 很少触发。
- **怎么验**：在 DGX 上用 `celadon_render`，跑 T-085 的 13 首 × 流媒体 −10 / −14 × 俱乐部 −7。期望：凡 I > L_t 的曲，输出 LUFS-I 在 L_t ± 0.5 LU 以内，限幅 GR 均值下降（melodic_241941 的 −14 组应降到 < 0.3 dB）；I ≤ L_t 的曲逐位不变（同决策重放对照）；标准档 22 首逐位不变；真峰值 ≤ Ceiling + 0.01 dB；再跑 `codec_tp_check.py` 看编码后真峰值是否随之下降（预期会，因为少了限幅产生的高频）。
- **对 Max 口味的核对**：直接服务「两版交付」与「根据音乐状态自动」。不碰收单和硬件建模，也不需要两遍渲染。

### R6-03 自动 Heat 底量：先实测能不能听见，再定去留

- **问题 / 现状**：算法 8 起，自动 Heat 恒为「底量 12 × 强度」（三种风格都是 12，`GlazeConstants.cpp:91,114,137`；T-032 R6 实验 E：默认 GLAZE 35 时 Heat = 4.2）。按 Heat 的公式（Mid 驱动 1+h、不对称 0.04h、湿路 0.25h，`ColorModule.cpp:90-94,383-387`；Tube = tanh(d·x+b)−tanh(b) 再按原点斜率归一，`Saturator.h:33`）估算单正弦的谐波（未计高频保护与过采样滤波）：

| Heat | 输入峰值 −12 / −6 / −1 dBFS 时 H3 相对基波 | H2 |
|---|---|---|
| 4.2（默认 GLAZE 35） | −85 / −74 / −66 dB | −113～−106 dB |
| 12（GLAZE 100） | −74 / −63 / −56 dB | −94～−88 dB |
| 35 | −62 / −51 / −44 dB | −74～−69 dB |
| 70（温润上限） | −52 / −42 / −36 dB | −60～−57 dB |

  这些谐波还只加在 150 Hz 以上的 Mid / Side 上，而 House 的能量大头在低频。底量这一档很可能在密集的混音里听不出来。代价却是实打实的：自动时 Heat 湿路一直开着，48k/512 下 Color 一级从手动的 0.141 % 涨到 0.35～0.37 %（T-021 `modules-after-T020.log`，包含 Glue 的开销）。
- **提案**：先做一个只量不改的对照，再在两条路里选一条。
  1. 对照：同决策重放（ADR-016），只把 `color.heat` 置 0，得到「底量 Heat 的贡献」差信号，量它的电平、频谱和 K 加权响度，再请 Max 做 ABX。
  2a. 听不出 → 自动不开 Heat（底量置 0），Heat 湿路走现有的空闲跳过，省约 0.1～0.2 pp CPU；Color 卡片如实显示 0。
  2b. 听得出、而且 Max 想要「God Particle 式的染色」→ 底量按风格提到可闻（这个数交给 R4 / R5 用试听标定，例如温润 / 冲击 / 通透分别取不同值）。这样「一插就有颜色」才名副其实。
- **依据**：公式【一手：源码】；谐波数值是 numpy 估算【推断】；Heat 对响度、峰值的影响在千分之一 dB 量级，出自换算表（`GlazeConstants.h:297-311`）【一手】；「自动 Heat 承担不了削峰、只留风格底量」见 T-032 R6-01 与 `GlazeConstants.h:340-346`【一手】。
- **对硬约束与 ADR 的影响**：对照本身不改代码以外的任何东西。2a / 2b 只在 GLAZE > 0 时改变输出，GLAZE 0 逐位不变；旧工程在 GLAZE > 0 时会变（实时 GLAZE 本来就不保证旧工程逐位相同，ADR-030 后果第 1 条）。零延迟（Color 的 64 样本延迟固定，不受影响）。
- **代价与风险**：对照为 S（渲染工具需要一个「重放时覆盖 color.heat」的开关，如果现在还没有的话）。2a 是 S，2b 是 S 加试听标定。风险：「听不出」要在 Max 的监听环境里判，合成正弦的估算不能代替。
- **怎么验**：DGX 上 `celadon_render` 跑 22 首 + 9 首 House，GLAZE 35 / 100，加 `--replay` 的 heat = 0 对照，量差信号 RMS 相对母带的 dB 与 1/3 倍频程分布；`bench.mm modules` 量 Color 一级前后的 CPU；ABX 结果写进报告。
- **对 Max 口味的核对**：God Particle 式的染色是他的明确目标，所以本提案不建议删掉 Heat 这一级，只要求自动底量要么真有效果、要么不白花 CPU。

### R6-04 监听级合并：一个 MonitorStage，离线导出一律旁通

- **问题 / 现状**：末端现在有四种临时监听：Listen（`CeladonChain.cpp:559-694`，乘法平滑 20 ms）、原声（经 Listen 的 `listenOriginalDb`）、试听差值（`differenceMix`，20 ms）、归一化预听（`ReleaseSafety`，线性平滑 50 ms）。它们之间的交接写了约 30 行特例（`CeladonChain.cpp:305-336`），历史上两次出过阶跃 bug（T-032 R8-01 / R10-03）。离线时预听被强制关掉（`:166`、`:304`），Listen 却没有关（`:367` 只看预听）：开着 Listen 导出，成品会被衰减掉「处理后比原声响的那部分」（最多 24 dB）。规格靠帮助文字提醒「导出前关闭」（`设计规格-Limit.md:92`、`设计规格-界面.md:126`）。
- **提案**：把四种监听合成一个 `MonitorStage`，放在 OUT 表和 GLAZE 出口之后、抖动之前。它只有一个增益平滑器和一个信号源交叉淡化器，模式是 {母带、等响、原声、差值、预听} 五选一，增益统一「只衰减」。离线（`isNonRealtime`）时整级逐位旁通，和现在的预听一致；抖动不属于监听，留在它之后、离线照常生效。
- **依据**：现有交接代码与 bug 史【一手：源码、T-032 R8 / R10】；「监听改动不进测点」的现行口径（设计规格-总体 2026-09-28 修订）【一手】；离线不自动关 Listen 是读代码确认的【一手】。
- **对硬约束与 ADR 的影响**：母带输出逐位不变（监听级全关时逐位旁通）。离线 + Listen 开这一种组合的输出会改变（不再被衰减），这是要修的行为，**需 Max 确认口径**（待拍板 4）。ChainTests 里 Listen / 预听 / 原声交接的用例要按新状态机重写，覆盖面不能减少。零延迟。
- **代价与风险**：M。风险：交接的语义要逐条保住（例如「预听退出时 Listen 接手斜坡」），改写时容易漏，要先把现有用例当作合同。
- **怎么验**：ChainTests 现有的 Listen / 预听 / 差值用例全部保留并通过；新增两条：「离线 + Listen 开」的导出与「离线 + Listen 关」逐位相同；任意切换序列下监听增益没有单样本跳变（逐样本差分 ≤ 一个平滑步长）。在 DGX 上跑。
- **对 Max 口味的核对**：不改声音，只消除「忘关等响导出变轻」这类事故，符合「简单、可解释」。

### R6-05 新动态处理的落位规则（共振 / 密度 / 冲击 / 低频）

- **问题 / 现状**：R3 / R4 / R2 会各自提新算法。如果每个都新开一级，链会变长，延迟会加，「每个模块只管一件事」的可解释性也会变差。
- **提案**：先定落位规则，算法交给对应角度。

| 新处理 | 放哪 | 理由 | 延迟 / CPU | 交给 |
|---|---|---|---|---|
| 共振抑制（动态窄带衰减） | Balance 内部：复用它的分析帧（2～8 kHz 的 1/3 倍频程约有 20～180 个 bin，够做更细的峰检测），执行时追加窄 Q 动态峰值滤波器，与「推响不刺」的 7 段合并成一条路径 | 修正类处理放在非线性之前（iZotope 原则），零延迟 IIR 符合 ADR-001「不用 FFT 改增益」；画像照旧取 Balance 入口 | 0 延迟；估 +0.05～0.2 % | R3 |
| 密度 / 向上压缩 | Color 内部 Glue 之后、Heat 之前（「Glue → 密度 → Heat」），或者做成 Glue 的并联支路 | 向上压缩的检测要看 Glue 已经控制过的电平，免得把 Glue 刚压下去的部分又抬回来；Color 已有整级 Mix（手动），说明并联本来就是这一级的职责 | 0 | R4 |
| 冲击 / 瞬态 | 不单开一级：通过 Clip 与限幅器的分担比例（风格份额 `shareClip / shareLimit`）和限幅攻击整形来实现 | 放在 Limit 之前的瞬态增强会被 Clip / 限幅马上削掉，放在之后又破坏 Ceiling | 0 | R2 / R4 |
| 低频专用控制 | 不单开一级。已有的分工：Clay 只切次声；Glue 低侧最多比联动轻 3.2 dB；限幅器在持续低频上给快释放周期下限；Balance 管 40～160 Hz 的平衡。如果还要更强的低频控制，放进 Limit 的检测侧（分频检测、按带施压，Ozone IRC IV 的公开描述是「limits frequency bands that contribute most to these peaks」）【一手：Ozone 9 文档】 | 「多段限幅」在非目标里写的是「试听后再评估」，可以重开，但要放在限幅器内部，不能放在它前面 | 视算法而定 | R2 |

- **依据**：iZotope Learn、Ozone 9 Maximizer 文档【一手】；Color / Limit / Balance 的源码常数【一手】；落位理由【推断】。
- **对硬约束与 ADR 的影响**：规则本身不改代码。按规则实现时，每一项都要求「强度为 0 时逐位旁通」，GLAZE 0 逐位不变；共振落在 Balance 内，与 ADR-001（IIR 组、不用 FFT 增益）一致。
- **代价与风险**：规则是 S；实现 M～L，取决于 R3 / R4 / R2。风险：Balance 文件已有 1859 行，共振那块应拆成单独的类，由 Balance 调用。
- **怎么验**：每个新处理都过同一套门：强度 0 逐位直通、块长逐位一致、22 首门槛、48k/32 最慢块 ≤ 15 %、上报延迟不变。
- **对 Max 口味的核对**：不加按钮，不加预设；House 的低频走 Glue 分频与限幅器的低频释放，不会牵扯到自动收单（他已否决）。

### R6-06 参考侧链：多学几样，加一个等响对听

- **问题 / 现状**：侧链「Reference」只用来学 10 s 的 27 段相对频谱（`ReferenceSpectrum.h:22-36`），不学响度、PSR、宽度，也不能拿来对听（规格写明「不进主输出」，设计规格-总体 2026-09-28 修订）。
- **提案**：两步。
  1. 侧链上多挂一块 `LoudnessMeter`（K 加权 + 真峰值），学参考曲的主段响度、PSR、低频占比和每段 S/M 比，作为可选的交付目标或宽度上限交给决策器。怎么用由 R5 定：例如「交付 = 跟参考」时目标响度取参考的主段电平，并受 Ceiling 与 PSR 下限约束。
  2. 在 R6-04 的监听级里加第六种模式「参考（等响）」：把侧链按测得的响度差衰减到与母带等响，只在实时监听里生效，离线一律旁通。
- **依据**：现有侧链路由（`PluginProcessor.cpp:70-76`、`:639-655`）【一手】；用参考曲建目标的思路 T-038 已经在用【一手：规格 3.2 节】；对听的价值属于【推断】。
- **对硬约束与 ADR 的影响**：没接侧链时逐位不变。第 2 步要改规格里「参考不进主输出」这一句（只进监听、不进导出），**需 Max 拍板**。第 1 步约 +0.15 % CPU（参照 IN 表的开销，T-021：0.144 %）。零延迟。
- **代价与风险**：M。风险：参考曲和母带不同步播放时，「主段」判定要独立做一份（复用 SegmentLedger 的逻辑）。
- **怎么验**：无侧链时块长逐位一致；接上合成参考（已知 LUFS / PSR）时，学到的值误差 ≤ 0.2 LU；对听模式在离线下逐位旁通。
- **对 Max 口味的核对**：仍然是全自动（参考只给目标），不是预设系统。

### R6-07 抖动加一档「16 bit · 噪声整形」

- **问题 / 现状**：末端只有平坦 TPDF（`ReleaseSafety.cpp:130-140`），没有整形。House 的俱乐部版常以 16-bit WAV 交给 DJ 或下载店，淡入淡出、混响尾巴和前奏里的噪底就是 16-bit 平坦 TPDF 的噪底（约 −93 dB 相对满刻度正弦）。
- **提案**：抖动参数末尾追加选项「16 bit 整形」（只追加、不改已有下标）。用固定系数的误差反馈 FIR，44.1 / 48 kHz 各一套（取 F 加权的「最小可闻」设计）；≥ 88.2 kHz 时退回平坦 TPDF。整形器的状态在 `resetDitherSequence` 里随随机序列一起复位，保证导出可复现；削波要放在误差计算之外，防止满刻度附近振荡。
- **依据**：Lipshitz, Vanderkooy & Wannamaker, "Minimally Audible Noise Shaping", JAES 39 (1991) 836–852（附录给出多阶整形系数）【一手：论文】；Sony Super Bit Mapping 用自适应误差反馈滤波器，按掩蔽与等响度曲线整形量化噪声（Akune, Heddle, Akagiri, AES 93rd Conv. preprint 3371, 1992）【一手：论文摘要】。自适应版本太复杂，固定系数就够【推断】。
- **对硬约束与 ADR 的影响**：选关、平坦 16 / 24 bit 时逐位不变；新选项按逐样本状态运行，块长无关、逐位可复现。零延迟，CPU 每样本约 2×N 次乘加（N ≤ 9），可以忽略。
- **代价与风险**：S。风险：整形后的噪声集中在 15～20 kHz，之后再编码成有损格式时会白占码率，所以帮助文字要写「只用于最终 16-bit 交付，流媒体用 24 bit 或关」。
- **怎么验**：DGX 上做单元测试：静音输入 + 整形，噪声谱贴合设计曲线（±1 dB），F 加权或 ITU-R 468 加权噪声比平坦 TPDF 低 ≥ 10 dB；−1 dBFS 正弦长时间运行不振荡；关和平坦档逐位不变；块长逐位一致。
- **对 Max 口味的核对**：没有新旋钮，只多一个选项，服务交付；优先级低。

### R6-08 入口电平分级（Color 之前自动 trim、Limit Gain 还回）：建议现在不做

- **问题 / 现状**：Glue 阈值是绝对电平（−24 dB × Glue/100，`GlazeConstants.h:258`），Heat 的饱和程度随输入电平变（换算表按入口真峰值分 5 行），所以同一个手动旋钮值在 −20 LUFS 和 −10 LUFS 的混音上效果不同。Balance 的 −60 dBFS 静音门（`BalanceModule.cpp:92`）和分析器的绝对门远低于音乐电平，实际不受影响。
- **提案（评估结论）**：可以做的形式是在 Clay 之后、Color 之前加 trim T（把主段电平归到参考值，例如 −14 LUFS），同时 Limit Gain 减去 T。「出口还回」**必须在限幅器之前**做，放在之后会破坏 Ceiling。好处是 Glue / Heat 的手动值与电平无关，换算表可以收成一行。但现在不建议做：规划器已经按画像的 I / TP 换算了电平（`glueDetectorOffsetDb`、Heat 表），收益主要落在手动用户身上；代价是 GLAZE > 0 与 GLAZE 0 下手动 Glue / Heat 的含义不一致（GLAZE 0 必须 T = 0 才能保住逐位契约），反而更难解释。真正有价值的那一半（热输入往下）已经由 R6-02 覆盖。
- **依据**：源码常数【一手】；判断【推断】。
- **对硬约束与 ADR 的影响**：与 ADR-008 第 3 条「手动值 + 自动增量」的语义冲突（手动旋钮的作用对象变了）。零延迟。
- **代价与风险**：M～L。风险：T 的慢变化会调制 Glue 的工作点。
- **怎么验**：如果以后要做，用 Glue / Heat 在 −24 / −14 / −8 LUFS 三档输入上的 GR 与谐波一致性来衡量。
- **对 Max 口味的核对**：对「全自动」用户（Max）几乎没有感知收益，所以列为 P3。

## 5. 「删 / 合并一道工序」候选（用数据说话）

| 候选 | 典型用法下的动作量 | 删 / 合并能换回什么 | 结论 |

## 待用户拍板

1. **GLAZE 能不能往下拉**（R6-02）：流媒体 / 俱乐部档里输入比交付目标响时，允许自动部分为负、最多 −6 dB？能不能低于手动 Gain（现有合同是「手动增益是地板」）？标准档维持只推不减？
2. **目标频谱「自动」的斜率来源**（R6-01）：A（直接取 Tone 的参考斜率）还是 B（去掉斜率分量只修形状）？这一条与 ADR-020 待复核第 1 条（新实例默认开不开）一起定。
3. **Heat 自动底量**（R6-03）：对照实测后，如果听不出，选「自动不开 Heat」还是「把底量提到可闻」？后者的具体数交给 R4 / R5 标定。
4. **离线导出时等响（Listen）是否自动失效**（R6-04），和预听一致？
5. **参考侧链能不能进监听**（R6-06 第 2 步）：只进实时监听、不进导出，是否允许改规格里「不进主输出」那一句？
6. **要不要「16 bit 整形」抖动选项**（R6-07）：取决于 Max 交 16-bit 文件的频率。
7. **换交付后增益多快到位**（交给 R5）：换交付是用户动作，是否应该快速到位，而不是按 0.2 dB/s 慢慢爬？

## 范围外发现（只报不改）

1. 任务书写的是「27 段 RBJ 并联峰值」，代码是**级联**（`BalanceModule.cpp:728-747`：样本依次过各段）。相邻段的相互影响正是 T-032 R2-02（串扰补偿）的前提，请写报告的代理不要按「并联」去推理。
2. Balance 最低段的分析泄漏：48 kHz / 2048 点下「40 Hz 段」只读 46.9 Hz 一个 bin，Hann 主瓣把 20 Hz / 25 Hz 内容以 −8.0 / −5.2 dB 计入（估算，`BalanceModule.cpp:316-343`）。次声多的歌，Balance 的最低段与 GLAZE 画像的低频证据都会偏高。这可以作为 R2-04 / R7 低频分辨率待拍板项的补充证据。
3. 换交付后增益按上行 0.2 dB/s 爬，主段度 < 0.5 时只降不升（`GlazeController.cpp:453-461`、`:606-625`、`:1154-1159`）。俱乐部版和流媒体版来回切换后如果立刻离线导出，开头一段（+3 dB 约要 15 s 主段时间）响度不到位，而 `coldExport` 只看置信度，不会提示。交给 R5。
4. 离线导出时 Listen 不会自动关（`CeladonChain.cpp:367`），只有预听会关（`:166`、`:304`），靠帮助文字提醒（见 R6-04）。
5. 设计规格-总体「信号链」一节的图仍然是 Balance → Color → Limit（没有 Clay），只在后面的「v0.1.7.0 修订」里补了说明；ADR-009 决定 1 里「零延迟 IIR」的写法也已被 ADR-012 / 014 改为固定延迟 D + G。属于档案表述过时，不影响代码。
6. T-085 报告把「−14 组实测中位 −12.01」主要归因于预算 / 守护。按它自己的数据，9 首里有 4 首输入就比 −10.5 LUFS 响、又没有往下的路径，这是另一个主要原因（R6-02）。
