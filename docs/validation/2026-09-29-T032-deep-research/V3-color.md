## R3-01 Glue 分频施压：mid 检测器驼峰 + 二阶分裂相位凹陷 —— **confirmed，high / P1**

**代码证据（自己找到的）**：
- 分频器 RBJ 二阶、Q = 0.7071：`ColorModule.cpp:50`（`butterworthQ`）、`:439-440`（`glueLowpass` / `glueHighpass` 设计）、`:330-362`（`designHighpass` / `designLowpass`）。
- mid 检测器 = hp − low − high：打包路径 `:1090,1093`，标量路径 `:1131`（`detectedMid = hp - detectedLow - detectedHigh`）。
- 三路包络 `:1238-1240`；Δ = `jlimit(−0.6, 3.2, (reductionDb − 本路) × 0.5) × glueOn`：`:1247-1252`；常数 `:70-72`。
- 音频施加 `midGain·(x − low − high) + lowGain·low + highGain·high`：`:1279-1282`。
- 表 / 统计只报联动 `reductionDb × glueOn`：`:1264,1267`。
- 现有测试只查「低比中少压 ≥ 1 dB」（`ColorTests.cpp:902-935`）与联动 GR 3～10 dB（`:937-954`），没有任何用例核对实际施加增益。

**独立数值验证（107，自写 Python 移植，与源码同常数、同运算顺序）**：
- 移植正确性：双音 90 Hz −16 + 2.5 kHz −8、Glue 100 → **+0.657 / −2.918 dB**，与 `docs/reference-chain-algorithm.md:82`（+0.66 / −2.92）和研究报告逐位一致。
- 频响（numpy，RBJ 系数）：|1 − LP₂(180) − HP₂(5k)| 峰 **+2.10 dB @ 230 Hz、+2.10 dB @ 3971 Hz**，@1 kHz +0.56；音频分裂 1 + 0.445·LP + 0.445·HP 最小 **−0.77 dB @ 303 Hz**，只抬低带 −0.75 dB @ 301 Hz。解析核对：二阶 Butterworth 在 fc 处 H = −j/√2，|1 − H| = √1.5 = +1.76 dB；|1 − H|² = (w⁴ + 2w²)/(1 + w⁴) 在 w² = (1+√5)/2 取极大 1.618 → +2.09 dB @ 1.272·fc = 229 Hz。研究的机理描述正确。
- 扫频（−6 dBFS、Glue 100、48 kHz、取 1.5～2 s 稳态）：现行相对联动静态曲线的偏差 229 Hz **−0.85**、300 Hz **−1.13**、400 Hz −1.05、2.5 kHz **−1.11**、3969 Hz −0.82、60～90 Hz +0.32、7 kHz +0.08、10 kHz +0.21；当晚修法（mid 跟联动）后 300 Hz −0.56、2.5 kHz **−0.65**（最坏）、跨频率幅度 1.45 → 0.76 dB。**与研究报告逐位相同**。
- **研究没测、核验补测的关键点——Glue 40（GLAZE 100 对应值，`ColorTests.cpp:373`「Tone +0.75、Glue 40、Heat 30」）**：−6 dBFS 纯音的联动 GR 只有 1.24～1.31 dB，现行实际却多压 229 Hz **−0.63**、300 Hz **−0.62**、2.5 kHz **−0.50**、3969 Hz **−0.64**（相对联动 GR 约 **50 %** 的误差）；当晚修法后全部落到 **−0.14～+0.06 dB**。原因：软拐点是二次曲线，+2.1 dB 的检测器驼峰在拐点段被放大，Δmid 直接钉在 −0.6 钳位——在 GLAZE 常用的浅压区这个伪像**占主导**，而不是研究报告强调的 Glue 100 相位凹陷。
- 低音主导的反向双音（150 Hz −8 + 2.5 kHz −16，研究没做）：现行 150 Hz −1.91 / 2.5 kHz **−2.96**（联动 −1.94）——**更轻的中频反而比响的低音压得更深**，与「响的一侧保持原来的压缩、轻的一侧少挨压」正好相反；修法后 −1.72 / −2.61（余下的 −0.67 是高带 Δ = +3.2 经 HP₂(5k) 在 2.5 kHz 处 Re < 0 造成的凹陷，属跟进项）。

**反驳点（研究报告里不准确的地方）**：
1. 「规格承诺『中频跟联动』」是误读：`docs/reference-chain-algorithm.md:50` 与规格 2026-09-28 段的「中频跟联动**攻击**」说的是攻击时间（低 36 / 中 20（同联动）/ 高 8 ms），规格明写「每路……各有自己的压缩量包络」「比联动重时最多再深 0.6 dB」。所以 −0.6 dB 这部分**在规格字面之内**；真正超出规格描述的是相位凹陷（≤ 0.77 dB）和「−0.6 被伪像而非真实中频响度触发」。但代码常数注释 `:66`「中频跟联动包络」与实现矛盾——当晚修法恰好让代码与这条注释、与 `ColorModule.h` 头注释「响的一侧保持原来的压缩」一致。
2. 该规格段是 T-029 对 Cursor 提交 `78896d3` 的**补记**（规格原文「执行方是 Cursor……没走档案 SOP」；TASKS.md 第 111 行：「Mac 整插件验收、22 首门槛、等响试听都没做」），不是 Max 拍板的取舍，改它不违背任何 ADR。
3. 「Δmid 触到 −0.6 钳位」：Glue 100 纯音下 Δmid ≈ −0.53（未到钳位）；Glue 40 下才钉在钳位。结论不变，措辞要改。

**严重度 / 优先级**：维持 **high / P1**。理由不是 Glue 100 的 1.13 dB，而是 GLAZE 默认工作区（Glue ≤ 40）里施加量比表读数深约 50 %、频率特征是 230 Hz 与 4 kHz 两处「中频挖坑」，且表不显示。

**修法**：
- 当晚（S）**OK**：`:1090,1093,1131` 不再算 midPeak；`:1239` 删 `midReductionDb` 推进；`:1251-1252` `midDb = gainDb`；`:1253` `useSplit = deltaLow != 0.0 || deltaHigh != 0.0`；`:1260-1261` `midGain = gain`；`ColorModule.h:218,220` 的 `glueMidPeaks` / `midReductionDb` 及 `:562,:671` 清零同步删；`:449` 的 `glueMidPeaks.assign` 删。Glue 关 / Δ = 0 的逐位契约保留（`useSplit` 分支与 `gainDb == 0.0` 短路不动）；现有 ColorTests 全部是自对照或只查方向 / 联动读数，不会失败。规格补一段带日期的修订（mid 不再有自己的包络、每样本少 1 次 log10 + 1 次 exp），`docs/reference-chain-algorithm.md:50,82` 与 `:66` 注释同步。
- 研究提议的新测试「输出 / 输入 RMS 与 `getAndResetGainReductionDb() − 6 dB` 之差」**要改一处**：`getAndResetGainReductionDb` 是窗口内**最大值**，正弦上 dB 域包络有纹波（60 Hz 最明显），用最大值会把偏差读大；应改用 `getBlockStats().glueGrMeanDb` 按块加权平均，或直接与「只联动」参照实例的输出比。阈值 0.7 dB 对修法后的 −0.65 只剩 0.05 dB 余量，建议 0.75。
- 跟进（L）**不是当晚**，且研究漏了一个风险：LR4 + 全通方案在 Glue 开着时输出恒带全通相移，`splitIdle` 一到就切回原信号，等于在淡出结束那一刻从 AP(x) 跳到 x——180 Hz / 5 kHz 附近相位跳变，「glue 100 → 0 no level dip, bit-exact after」（`ColorTests.cpp:1196`）这类用例即使过，也可能有可闻的切换；要么按 glueOn 在 x 与 AP(x) 之间交叉淡化（淡化期间交叉点附近有梳状抵消），要么全通常驻（Glue 关时不再 null）。这是产品级取舍，要 Max 定并试听；`glueBandDeltaMaxDb` 3.2 → 1.5 的临时缓解会把双音的低音保护从 +0.66 砍到约 +0.3，同样要 Max 定。

**风险**：当晚修法改变 Glue 开着时的输出（只在 Δ ≠ 0 的样本）；GLAZE 规划器的 Glue 实测常数（`GlazeConstants.h:151-153`，响度损失 1.05 × 平均 GR、真峰值 0.95 × 平均 GR）是分频前（v0.6）量的，分频后没复核，修法把关系拉回分频前方向，仍应在 22 首门槛重跑时看一眼（见「漏掉的问题」1）。

## R3-02 Glue 增益计算器 4× log10 + 4× exp —— **confirmed，medium / P2（研究 P1 夸大）**

**代码证据**：`reductionTargetFor` 每次 `20·log10(min(peak, 1e30))`（`:1198`），`peak ≤ kneeStartLinear` 短路（`:1195`）；联动调用 `:1215`，三路经 `bandTarget` `:1235,1238-1240`；`std::exp` 四处 `:1254,1257,1259,1261`，低 / 高 / 中在 Δ = 0 时复用 `gain`。**属实**。

**独立基准（107，g++ 15 −O2，4M 随机峰值）**：4× log10 + 4× exp（double）**47.7 ns/样本**（复跑 47.6）；4× log10f + expf **25.7**；**分频前的 1× log10 + 1× exp 15.1 ns**——分频把这块放大 3.2 倍。研究测得 69.5 是它的循环写法不同（含 jmin 等），量级一致；48 kHz 下 2.3～3.3 ms/s ≈ 0.23～0.34 % 单核。

**反驳点**：
1. 「超过 Heat 整条 8× 链」**未证实**：研究把文档的 0.44 %（Glue 关 0.16 % → GLAZE 100 0.60 %）全归 Glue，但 GLAZE 100 = Glue 40 + **Heat 30** + Tone 0.75，Heat 30 时 8× 湿路整条在跑，那 0.44 % 大半可能是 Heat。M2 Pro 上 v0.5 实测（分频前）默认 0.11 % → GLAZE 100 0.32 %，其中 Glue 40 单路超越函数约 15 ns ≈ 0.07 %，Heat + Tone ≈ 0.14 %；分频后 Glue 约 ×3 → 0.2 %，与 Heat **同量级**而非「超过」。排序要 `tools/perf` 在 Mac 上分级实测（ADR-007，Max 跑）。
2. 成本估计是 **Glue 100 + 响素材** 的上限：侧链峰值是**瞬时** |x|（`:1004,1029`）不是包络，Glue 40 时拐点起点 −12.6 dBFS，−6 dBFS 正弦有 30 % 样本、类音乐大多数样本走 `:1195` 短路不算 log10；exp 四次在 Δ ≠ 0 时总要算。GLAZE 常用区实际约为估算的一半。
3. 「changes_output ≤ 1e-6 dB」偏小：rel. err 1e-7 的 log2 在 log2(p) ≈ 5～100 时绝对误差到 1e-5，折 dB 约 6e-5 dB（≈ −100 dBFS 的相对差），仍不可闻，但数字要写对；`glueSnapDb = 1e-6` 的归零判断不受影响（只影响包络尾巴是否早一两个样本归零）。

**修法**：
- 第 1 步随 R3-01 自动得到（−25 %）：OK。
- 第 2 步 4 路 double SIMD `fastLog2` / `fastExp2`（无 FMA、三平台同一串 IEEE 运算，同 `Saturator.cpp:139-178`）：方向正确，且**顺带把 Glue 开着时的输出从「依赖各平台 libm 的 log10 / exp 末位」变成跨平台确定**（现在 Mac / glibc / MSVC 的 libm 末位本就不同，Glue 开着时各平台从来不逐位）。但需要：极小极大系数、±0 / Inf / NaN 行为（NaN 峰值现在被 `jmax(0.0, |NaN|)` 挡在峰值外 `:1004`，log 输入恒 > kneeStartLinear > 0，可不管 NaN 但要写明）、新精度用例、x64 上 2× `__m128d` 拼 4 路——**M 级、新增一片逐位契约面，不该压在「今晚全部落地」里**。
- 第 3 步「零风险过渡」（换 `8.6859·log` 或 float `log10f/expf`）**不是零风险**：改了每个 Glue 开着的样本的末位，收益 0.05～0.1 %，没有可听好处；要么不做，要么一步到位做第 2 步。

**严重度 / 优先级**：medium / **P2**。

## R3-03 Heat 8× 倍率与采样率无关 —— **confirmed（事实），low / P2（研究 medium / P1 夸大）**

**代码证据**：`prepare` 对任何采样率加三级（`:467-469`）；注释「旧 Heat 驱动 10 时 4× 折返 −56.7 dB」（`:460`）；现行驱动 1 + h（`:78,364-368`）、残差 0.25h（`:79,655`）、Side 1 + 0.5h（`:81,706`）；延迟 64 与采样率无关（`ColorTests.cpp:1172-1193`）；混叠测试只 48k / 10 kHz / −6 dBFS（`:557-610`）；近似链只用第 1 级、延迟 49、补 15（`:507-514`）；两级延迟 60 见 `HalfBandOversampler.h` 头注释与 Limit。**属实**。

**独立验证（numpy，65536 点单周期，Tube drive 2 / asym 0.04，残差 ×0.25，相对输出基波）**：0 dBFS h3 −31.5、h5 −44.4、h9 **−69.6**、h19 **−132.6** dB；折返最坏：48k×8 −132.6（h19 → 4 kHz）、**48k×4 −69.6（h9 → 12 kHz）**、**96k×4 −132.6（与 48k×8 逐项相同）**、44.1k×8 / 18 kHz −132.6、48k×4 / −6 dBFS 10 kHz −205.7。与研究一致（差 1 dB 是基波参照不同）。规格 v0.5 段「44.1 kHz 18 kHz 折返 −56.8 dB」确已过时（现行映射 −133 dB）。

**反驳点**：
1. 收益被夸大：M2 Pro 整链 48 / 96 / 192 kHz 实测 1.3 / 2.6 / 5 %（`docs/reference-chain-algorithm.md` 性能段），192 kHz 离 10 % 预算还有一倍；Color 在整链里约 15～20 %，Heat 湿路是 Color 的一部分，方案 A 在 192k 省的是整链约 3～5 %。x86 虚拟机 192k 的 13 % 超预算是 Balance 频谱分析等在拖，不是 Heat。
2. 研究漏的三处：① 新加的 `BlockDelay`（4 或 15 样本）在 `heatInputScratch` 之前，就必须进 `primeHeatOversampler` 的预热回路（`:1410-1445`）并在 `reset` / `primeHeatOversampler` 里清零，否则重开后前 4 / 15 个样本对不齐、破坏「跳过与不跳过逐位相同」；② 96k 以上输入合法含 20～48 kHz 超声内容，40 kHz 分量的 h9 在 384 kHz 内部速率下折到 24 kHz——不在研究的「< 20 kHz」分析里（实际电平极低，但混叠用例要把 ≥ 20 kHz 段也扫一遍）；③ `coefficientUpdateInterval` 改 `2 × oversamplingFactor` 会同时改 `processHeatWhileIdle` 的计数（`:1505`），两处要一起。
3. 方案 B（48k 也降 2 级）改变旗舰采样率的输出、只剩 10 dB 混叠余量（0 dBFS 20 kHz 极端），研究自己也不推荐——同意不做。

**修法**：方案 A 可行、44.1 / 48k 逐位不变的论证成立（级数不变、补偿延迟为 0 时 `BlockDelay` 是纯搬运）。但它改的是 Color 里契约最密的预热 / 空闲状态机，验收要在 96k / 192k 上跑「idle skipping bit-identical」「block-size independence」「re-enable after long idle」全套 + 新混叠用例；**不是当晚项**，先让 Max 用 `tools/perf` 看 96k / 192k 的 Heat 占比再决定。

## R3-04 M/S 150 Hz 高通未打包；残差相减多一次拷贝 —— **confirmed，low / P2，修法 OK**

**代码证据**：`prepareHeatInput` 立体声分支对 Mid / Side 各走标量 `processBiquad`（`:1343-1350`），而 Tone `:900-939`、侧链 `:985-1017`、分频 `:1054-1114` 都用 `StereoBiquad`；打包与标量逐位相同的论证在 `:148-224`（`PackedPair` / `StereoBiquad`）（ARM 融合 / x64 不融合两边一致），测试 `ColorTests.cpp:2190`（L = R vs 单声道）、`:2228`（L ≠ R 打包 vs 标量，剧本含 Heat 60 / 100）。`processResidualBlock` 先 `memcpy` 到 `heatResidualScratch` 再 `processTubeBlock` 再逐样本相减（`:1366-1373`），调用点三处（`:1437,1464,1550`）。**属实**。

**逐位不变核对**：① M/S 打包：Mid / Side 先在 float 里算好（`:1347-1348`），再 `loadStereo` 转 double，双二阶每一步与标量同一 IEEE 运算，无跨通道运算——与 Tone 的论证相同；单声道与 > 2 声道仍走标量。② `Saturator::processTubeResidualBlock`：lambda 返回 `vSub(vMul(vSub(tanh4(vAdd(vMul(d,x),b)), offset), inverse), x)`——`vMul` 结果先舍入成 float，再减同一个 float x，与 `data[i] -= scratch[i]` 同一运算同一操作数；尾巴补 0 的 lane 得 `fastTanh(b) − fastTanh(b) = 0`，丢弃。逐位不变成立，`heatResidualScratch` 可删。**收益**：每 1× 立体声样本约 5～10 ns，低。可以当晚做（S），但优先级在 R3-01 之后。

## R3-05 Heat = 0 时近似残差链常驻 —— **uncertain，low / P2，建议不做**

**代码证据**：`proxyWanted = heatDcProxyEnabled && heatSmoothed.getTargetValue() == 0.0f`（`:1569`）；每块 `runHeatProxy`（`:1606-1612` → `:1447-1478`）：第 1 级半带来回 + `proxyTube` 残差 + 直流增益补齐 + 对齐延迟。**属实**。

**反驳点**：
1. 这是**规格明文接受的设计**：`设计规格-Color.md` v0.5 段第 3 条「唯一不逐位的地方：湿路静止期间 5 Hz 直流阻断改吃 2× 近似湿路，与 v0.4 定义差 ≤ −90.6 dBFS（满幅白噪）/ −138.5 dBFS（类音乐）」，测试 `ColorTests.cpp:2098-2183` 以 −80 / −110 dBFS 把关。研究的修法是拿这个已验收的界去换约 30 % 的近似链成本——按 M2 Pro 默认 0.11 % 估，省的不到 0.03 % 单核。
2. 可行性估计偏乐观：直流阻断状态 = 残差里 < 5 Hz 的成分；对满幅白噪，残差的 < 5 Hz 功率占残差约 5/24000（−37 dB），残差本身约 −20 dB，状态误差量级 −57 dB；重开时 256 样本预热只收敛 1 − e^(−256/1527) ≈ 15 %，mix 淡入 20 ms 内再衰 ≈ 50 %，乘湿路上限 0.25 → 输出误差量级 **−70 dBFS 上下**，很可能过不了白噪 −80 dBFS 门槛（研究自己置信度 0.6、写明「超界则放弃」）。
3. 研究漏的连带：空闲路径里 `protectHeatResidual`（`:1517`）也在吃近似残差维护 `heatGuardLow`（4 kHz 一阶）与 30 ms 能量平滑的历史；停掉近似链后这两处也要重新预热，否则重开后高频守护的第一次判断（32 样本后）基于错误历史。
4. 若将来真要省这块，更便宜的候选是 **1× 近似**（不过采样，只做 tanh(x) − x，成本约现在的 10 %）——但 < 5 Hz 成分会混进 1× 下的折返，同样要按 `:2098-2183` 用例实测才知道是否守得住 −80 / −110 界。

**结论**：不确定能否守住已接受的界，收益极小，风险在两处状态；**建议不列入落地清单**。

## R3-06 湿路比例 `heatMixSmoothed` 未经 64 样本延迟 —— **refuted（事实成立，但不是缺陷）**

**代码证据**：makeup 用 `heatDelayedScratch[i]`（`:1634` 延迟、`:1650` 查表），`useProxy` 也看它（`:1657`），`mix = heatMixSmoothed.getNextValue()`（`:1651`）不延迟；两者同为 20 ms 线性平滑（目标 `:652,655`，平滑 `:541-542`）。**事实属实**。

**为什么不是缺陷**：
1. 「对齐」的前提不成立。驱动量在 `processTubeSegments` 里按 `heatScratch[j / oversamplingFactor]`（`:1535`）施加——即按**本块 1× 索引**取未延迟的 Heat 值，而 Tube 位于上采样链之后、下采样链之前：输出样本 i 的内容来自输入 i − 64，驱动它的 Heat 值是 Heat(i − L_down)，L_down ≈ 27（第 1 级下采样 0.06 / −75 dB 比上采样 0.05 / −90 dB 短，三级合计上 ≈ 37、下 ≈ 27，按等纹波长度比例估，精确值要 JUCE 设计函数）。所以 makeup 的 64 样本对齐**自己就差约 27 个样本**，规格「经 64 样本延迟对齐」是近似说法；把 mix 也延迟 64 只是换成与 makeup 同样地「晚 37 个样本」，并不更对。
2. mix 是交叉淡化，本无对齐要求：Heat 0 → X 的头 27 个样本里 mix ≤ 0.25·h·(27/960) ≈ 0.7 %·h，混进的是 Heat 0 残差（tanh(x) − x，本身 ≤ −40 dB）——幅度 −80 dBFS 量级、1.3 ms，不可闻；X → 0 对称。
3. 无功能后果：`useProxy` / `isHeatWetIdleCondition` / `heatIdleSamples` 的顺序在现有写法下自洽（mix 先落 0、延迟后的 Heat 再落 0、驱动量更新到 0、再计 256 样本），研究也只说「多一种状态」。改成从 `heatDelayedScratch` 推 mix 要同时动 `:1330-1336,1654`，为一个不可闻的差别去碰空闲跳过的条件，收益为零。

**结论**：不改。若要动，只改文档：规格里「经 64 样本延迟对齐」补一句「驱动量在过采样链中段施加，对齐是近似」。
