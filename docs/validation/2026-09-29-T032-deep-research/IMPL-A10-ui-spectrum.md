修坯斜线的差不是缓存引入的错误，而是**改前的斜线本身随面板在窗口里的位置变**：同一份改前代码、同一状态，面板放在 (0, 0) 与 (84, 60) 画出来，斜线区有 889 个像素差到 5 LSB（改后两处只差 1 个像素）。机理：斜线正好 45°，JUCE 边表（`juce_EdgeTable.cpp` 的路径构造）按 `stepSize = 256 / (1 + (int) |dx / dy|)` 决定每个像素行在 1 个还是 2 个子行上取边的位置，而 `dx / dy` 由变换后的浮点坐标相减得出，落在 1 的哪一边取决于绝对坐标的舍入。用 numpy 的 float32 逐步复刻 `addLineSegment` → 平移 → 边表斜率：低切 32 Hz 的 44 条斜线共 176 条边，平移 (1, 1)（改后缓存图在 ×1 时的偏移）与 (0, 0) 的步长全同，平移 (84, 60) 有 53 条边换了步长。改后斜线画进底层缓存，与面板位置无关，与改前在 (0, 0) 处画的只差几个像素（斜线区 3 个 ≤ 1、左下圆角 11 个 ≤ 2）。

## 3. 逐条说明

文件：`Source/ui/SpectrumAnalyser.{h,cpp}`、`Source/ui/SpectrumView.{h,cpp}`、`tests/SpectrumAnalyserTests.cpp`（任务书限定的五个）；没有新建源文件，没碰 `SnapshotMain`、估计量口径。

### R9-04 ① 竖纹与渐隐

- `SpectrumView::prepareStripes`：一张 ARGB 瓦片，**一行高、整面宽**（`ceil (1032 × 像素比) + 1` 像素），用与原来逐条 `fillRect (x, 0, 0.8, h)` 相同的逻辑坐标、像素比与颜色栅格化（相位以组件原点为 0），画之前先把裁剪区换成边表——原来的竖纹是在边表裁剪区里画的，新图默认的矩形列表裁剪区走另一套浮点矩形抗锯齿，边缘覆盖会差 1。像素比或颜色（OUT 开关改透明度）变了才重生成。
- `paint`：`setFillType (FillType (stripeRow, scale (1 / 像素比)))` + `lowResamplingQuality` 后 `fillPath (outputFill)`；渐隐 `setGradientFill` + `fillPath (outputFill)`。原点在整数像素上时变换只剩整数平移，软件渲染器走 `renderImageUntransformed` 的平铺；CoreGraphics 是 `CGContextDrawTiledImage`。
- 与任务书的差别：任务书写「宽 round (2·像素比) 的小瓦片」。非整数像素比（×1.25、×1.75）下 2 逻辑像素不是整数个设备像素，小瓦片的周期会取整漂移；整面宽的一行在任何像素比下条纹间距都正好 2 逻辑像素。
- 逐像素相同的写法试过（上一任）：裁到 OUT 后一次 `fillRectList` 516 条，×1 9.6 ms / ×4 63 ms，比瓦片（5.0 / 34 ms）慢近一倍，×4 与改前持平，不取；代价是 2.3 节「竖纹列」那类 ≤ 2 LSB 的差。

### R9-04 ② 静态部分缓存

- `SpectrumView::CachedLayer` / `Layer`：`back`（面板渐变 + 网格 + 修坯低切以下的斜线）、`frequencyText`、`dbText`、`readoutShadow`、`readoutBox`、`readoutBorder` 六张。`layerArea` 给每张的逻辑区域（四周多 1 px；底层是整个组件外扩 1 px，小数原点吸附后面板边缘不露底），`prepareLayers` 按此刻的物理像素比（`getPhysicalPixelScaleFactor`）生成：图左上角取整到设备像素（`origin = ⌊area × 像素比⌋`），图里每个像素与组件自己的设备像素网格同相位；`drawLayer` 用 `lowResamplingQuality` 贴，变换只剩平移（小数原点时整张吸附 ≤ 0.5 px，不双线性重采样）。
- 为什么拆成六张：同一张图里互相叠着的半透明元素「先合成再贴」与「逐个直接画」的整数舍入不同；拆开后每张里的元素互不重叠、都是往全透明上画一次，贴回去与直接画相同（2.3 节的数据证实）。
- 底层用不透明的 **RGB** 图（`d98f878`）：JUCE 9 软件渲染器往 ARGB 上混色按 ÷ 255 四舍五入、往 RGB 上按 × (256 − α) >> 8；半透明网格画进 ARGB 再贴回 RGB 的窗口后备图会差 1。macOS 的原生图把 RGB 当 ARGB 建（`juce_CoreGraphicsContext_mac.mm:300`），Direct2D 支持 RGB，都不出错。
- dB 刻度的白色圆角底框**不缓存**（`d98f878`）：半透明抗锯齿边先画进透明图再贴，个别边缘像素与直接画差 1（JUCE 对单个像素与成段像素的覆盖率算式不同）。6 个底框在构造时量好（`dbChips`），每次直接画，×1 0.023 / ×2 0.057 / ×4 0.155 ms。字仍是缓存图。
- 失效：像素比变（任何一张）；`resized`（底层与面板路径）；`setLanguage`（读数框三张，宽度随语言变）；`setClayMarkers` 只在斜线出现 / 消失 / 低切频率变时作废底层（`a229c0c`，只改收单频率不动底层）；斜率不影响任何缓存图（曲线路径另有失效）。修坯标记的竖虚线与标签、dB 底框、曲线、光标、读数文字每次照画。修坯标签文字与宽度在 `updateMarkerLabels` 里随频率 / 语言算好，paint 不再拼串量宽。
- 修坯斜线画进底层：画一次 ×1 0.5～0.9、×2 1.1～2.0、×4 2.3～4.4 ms（低切 32 / 100 Hz），缓存后只在低切变时付。代价是 2.3 节说的「与改前在 (84, 60) 处差 ≤ 5 LSB」——改前本身就随位置变。
- 内存：底层 ×2 约 3 MB、×4 约 12 MB（RGB 3 字节 / 像素；macOS / Direct2D 按 4 字节约 4 / 16 MB），其余五张与瓦片合计 ×2 < 1 MB。

### R9-04 ③ 悬停

- `setHoverFrequency`：重画旧光标列、新光标列（`cursorBounds`：光标横坐标 ±6 px、整高——1 px 虚线 + 8 px 圆点 1.6 px 描边都在里面），读数文字与上次画出来的（`shownReadout`）不同才重画读数框。
- `paint` 开头按 `g.clipRegionIntersects` 决定每一块画不画（OUT 填充、轮廓、平均线、IN、峰值、光标、两张刻度、读数框、两个修坯标记），必须在按面板圆角裁剪之前判断（之后裁剪区成了边表，只剩包围盒可比）。描边的包围盒按尖角接头最大外伸放大：JUCE 只在半斜接长度 ≤ 半宽 × 斜接上限 4 时用尖角（`juce_PathStrokeType.cpp` `addEdgeAndJoint`），描边最多伸出路径 2 × 线宽，所以用 `2 × 线宽 + 1 px`（`18f64d5`；第一次接续写的 1 × 线宽在曲线尖峰伸进脏区时会漏画）。
- 与任务书的关系：核验调整后的修法给了两条路——读数框 / 光标做成子组件（读数框 `setBufferedToImage`），或 paint 里按 `clipRegionIntersects` 跳过整块。走的是后者（同时缩小脏区），不新增组件、不改子组件层级；macOS 只拿包围盒，省得少（2.4 节「包围盒」一列 ×2 仍省 70 %，因为各块本身也便宜了）。

### R9-04 ④ 路径

- `buildCurvePaths`：OUT 轮廓建一次，填充 = 它的拷贝 `lineTo (右下)`、`lineTo (左下)`、`closeSubPath`。原来的填充是「左下起笔 → 480 点 → 右下 → 闭合」，有向边集合与方向完全相同，栅格化结果一样（2.3 节 OUT 内部逐像素相同）。平均线、峰值线、IN 虚线（已展开成填充路径）同样缓存；只在 `setSpectrum` 数据变了或 `updateTilt` 时作废——悬停不再重建。
- 改前每次 paint 都 `buildLine` 4～5 次（OUT 两遍，IN 开时再一条，悬停时也照建）；改后只在数据变了的那一帧建 3 条（IN 开时再展开一次虚线）。

### R7-05 / R9-10 预算

- `SpectrumAnalyser::updatePointRanges`（`setSampleRate` 里调）：用改前 `analyse` 的同一组 double 算式、同样的顺序算好 480 点的 `{first, last, t, interpolate}`（`2^±halfStep` 与点号无关，只算一次，值相同；覆盖 bin 数 = last − first + 1，R7-01 的 H_n 可以直接从这里取）；`analyse` 每点只查表、取最大或插值、一次 `log10`。插值那一句 `powerAt (first) × (1 − t) + powerAt (last) × t` 与原来是同一个表达式（clang 默认 `-ffp-contract=on` 时合并方式也相同；工程全局 `-ffp-contract=off`）。
- `SpectrumView`：构造时算好每点横坐标 `pointX` 与频率 `pointFrequency`（与原来画图时逐点现算的同一算式），换斜率时 `updateTilt` 算 `tilt[i]`（与 `tiltAt` 同一算式）；`buildLine`、`updatePeakReadout` 只做加法。横坐标与采样率无关。悬停读数与光标在任意频率上，仍用 `tiltAt`。
- 界面不在 ADR-013 的逐位契约范围内，逐位用例是回归保护。

### IN 关时跳过 IN 的 FFT

- `SpectrumAnalyser::setInputSpectrumEnabled / isInputSpectrumEnabled / hasInputSpectrum`：关着时 IN 的样本照收（环形缓冲、RMS 照算），只省每帧一次加窗 + FFT；关的一刻 IN 显示曲线落到底线。重新打开后，下一次有 IN 新样本的 `update` 直接取那一帧的测量值（不从底线按「升」爬——关着那段没有跟踪，爬上来会让人以为信号在变），在那之前 `hasInputSpectrum()` 为假。默认开：只用计算器的一方（测试、别的工具）与以前逐位相同。
- `SpectrumView::setSpectrum (SpectrumAnalyser&)`：签名从 `const&` 改成非 const，每帧（`update` 之后）把 IN 开关告诉计算器；`inputReady` 跟 `hasInputSpectrum()`，没就绪时不画 IN。编辑器里 `c.spectrum.setSpectrum (analyser)` 传的是成员，原样编过。全库只有频谱仪视图读 IN 的显示曲线（grep 核过）。
- 行为变化（IN 默认关，打开才看得到）：打开后 IN 最多晚一帧（33 ms）出现，且直接是当时的读数；宿主不送音频块时（有的宿主停播就不调用 processBlock）打开，要等再有样本才出现（改前是一条正在落下或已落到底的旧曲线）。列进待 Max。

### R9-11 FFT 封顶

## 4. 偏离任务书与没做的

1. **×1 / ×2 不是逐像素相同**（V9 写「截图断言只在 --scale 1/2 下要求逐像素相同」）：OUT 抗锯齿边上的竖纹像素 ≤ 2 LSB（×1）/ ≤ 1 LSB（×2），是瓦片平铺固有的舍入顺序差，唯一逐像素相同的写法（fillRectList）慢近一倍、×4 不省；修坯斜线在编辑器位置上 ≤ 5 LSB，是改前本身随位置变。其余逐像素相同。
2. 非整数比例下渐隐改 fillPath 带来面板最底一行（部分覆盖）的差，×0.7 时最大 4～6 LSB；换回原画法能消掉但每帧贵 0.6～2 ms 且违背任务书，没换（2.3 节）。

4. 竖纹瓦片是一行整面宽，不是 2 逻辑像素宽的小瓦片（理由见 3 节 ①）。
5. dB 刻度白底框没缓存（逐像素一致）。
6. 「改前把 480 点结果存成快照」做成「测试里抄改前算法当参照」+ 摘要记录（理由见 2.2）。
7. R9-04 的验证写的是 `ui-snapshot --bench`：截图工具归 A9，本线没加；计时用草稿工具（同一套 `ComponentPaintDiagnostics`），见 2.4。
