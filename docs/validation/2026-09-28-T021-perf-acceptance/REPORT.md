# T-021 · v0.1.7.1 整插件性能验收（对 v0.1.6.2）· 2026-09-28

会话「bench 补 Clay」（Opus 5.5，单线、不派代理）。只跑基准，没改插件源码。

## 1. 结论

**没过**设计规格-Clay-分析决策与验收 第 5 节的预算。

| 预算（对 v0.1.6.2） | 实测（5 个场景 × 2 轮） | 结论 |
|---|---|---|
| 48k / 512 平均增加 ≤ 0.15 个百分点 | +0.17 ～ +0.30（均值 +0.24） | 约 2 倍 |
| 192k / 32 最坏块增加 ≤ 0.5 个百分点 | 结构性最坏 +0.75 ～ +2.05（均值 +1.38） | 2 ～ 4 倍 |

- 不是尖峰：修坯每块都有的常态开销，最坏块也跟着整体抬高。
- 其中约七成是峰值守护（ADR-014）；原预算写于守护之前。
- 修坯中性（GLAZE 0、三项为 0、输出 = 输入延迟）时守护照样全速在算，而这时它的 g 恒为 1。
- 要达标，守护得便宜约 3 倍（48k），192k / 32 那条几乎要做到零开销。
- 决定交给 Max（2026-09-28 Max：「给我 Prompt 我让别人处理」），提示词见第 7 节。

## 2. 测什么、怎么测

- 当前：真工作树源码 = v0.1.7.1（T-018 删自动收单 + T-015 + T-020）。用的是 07:59 增量编出的 celadon_bench；`perf-local.sh` 每轮开跑前都会增量编，08:01 ～ 08:10 观察进程没见到任何编译，说明这期间源码没变、没重编。
- 基线：`Celadon-releases/source-baseline-2026-09-26-v0.1.6.2` 的 `Source/` 与 `tools/perf/`，加当前 `JuceLibraryCode/`（Projucer 生成的包装文件，与 DSP 开销无关）。
- 两边 grid 模式代码一致：
  - 基线的 bench.mm 与 T-016 之前的当前版逐字相同；
  - 两边都打了同一个补丁（本轮新加的 `structWorst64k`），见 `baseline-bench.patch`；
  - runGrid 函数体只差 hop 的写法（内联与函数，同一算法）。
- 命令：`grid all 44100,48000,96000,192000 32,64,512 20 10 5`（空跑 20 s 让 GLAZE 听完，每遍 10 s、5 遍）。
- 顺序：基线、当前、基线、当前（08:01 ～ 08:10），接电源、非低电量。
- 干扰：另起观察进程每 2 s 查一次编译进程，全程没有（`compile-activity.log` 为空）。
- 07:51 ～ 07:58 的一轮与别的会话的 Xcode 构建撞车，作废，日志留在 `contaminated-0751/`。
- 看结构性最坏（按相位取中位数再取最大），不看单次最坏：192k / 32 的单次最坏被系统抖动主导，同一场景在 25 ～ 76 % 之间跳。

## 4. 开销在哪（sample 剖析）

- 做法：逐级基准 `modules manual 192000 32 2 600 1` 跑着时 `sample` 15 s，看栈顶计数（`clay-profile-top.txt`）。
- 修坯内部：
  - `ClayModule::PeakGuard::process` 1436，约 70 %；
  - `ClayModule::process` 主体（4 个低切双二阶、延迟线、M/S）468，约 23 %；
  - `LinearPhaseLowpass::process` 149，约 7 %。
- 逐级基准里修坯一级平均：48k / 512 约 0.19 ～ 0.20 %，192k / 32 约 0.77 ～ 0.83 %（块预算）；与场景几乎无关（三级影子运行，守护一直在算）。
- 守护每样本：写两个环、局部峰单调队列、包络、界、逐声道 g_req、代价格、前瞻最小单调队列、线性释放、长 A + 1 的滑动平均、输出混合。
- y 与 x 逐位相同时 g_req ≡ 1，g 路径收敛到全 1、可以精确重建；E（±8 ms 局部峰）与 P（1 s 包络）依赖干路，不能跳。

## 5. 顺带量到的（T-020、周期性重算）

- T-020 分摊预热 + 低通 O(1) reset 之后，192k / 32 切一次分频点：那一块多 0.38 µs，最坏块 +0.125 个百分点（改前 18.2 ～ 18.5 µs、+11 个百分点）。`modules-after-T020.log` 的 XOVER 行。
- LinearPhaseLowpass 与守护每 65536 样本一次性精确重算滑动和：192k 约 1.5 µs 的尖峰（修坯一级按 65536 相位的结构性最坏 1.75 ～ 1.80 %，平均 0.8 %）。
  - 目前不和 Balance 的 FFT 那一块重合：整块 `structWorst64k` 只比 `structWorst` 高 0.05 ～ 0.08 个百分点。
  - 但分频点切换后新低通从切换时刻 reset，它的重算网格可能对上 FFT 那一块（约 1 个百分点）。可以与守护优化一起考虑分摊。
