## 0. 结论

1. **守护拦得对，不过敏。** 两首参考曲只有低切在动（deep 10.59 Hz、tech 13.60 Hz；收单、加宽都是 0）。低切把被成品限幅器「算进去」的次声切掉后，原来被次声偏置压住的那一侧峰值冒出来：不守护时 deep 整首峰值 −0.64 → +0.72 dBFS。触发样本只占 0.22 ～ 0.34 %，但每次超界中位 0.27 dB、p90 0.76 ～ 0.84 dB（< 0.1 dB 的只占 22 %）。「70 ～ 81 % 的时长」是 100 ms 线性释放把这些触发拉长的结果，不是守护在芝麻量上乱动。T-043 的「去掉守护」对照（somggggg 入口峰值 +0.57 dB、WTF +0.84、will we be okay +1.18，门槛全失败）也说明守护必须留。
2. **入口不贴 0 dBFS**：两首原曲峰值 −0.64 / −1.07 dBFS，高于 −1 dBFS 的样本占比四舍五入为 0.000 %、高于 −0.3 dBFS 的没有。「入口已经贴着 0 dBFS」这个假设不成立。
3. **缺陷在守护上面那层：压力反馈（ADR-014 3a）该降档时不降档。** 3a 加压力反馈，正是为了「守护几乎一直在拉、低切相位残差被深度调制」时把自动低切降下来。但它的统计量是「每 10 ms 格超界 dB 的平均（没超界的格记 0）」，被大量 0 稀释；门槛却沿用先试的 0.2 dB，而先试量的是「100 ms 块峰值 P99 的比」。同一首歌上两者差约 4 倍：deep 按先试口径的滑动 10 s 代价中位 +0.35 dB、64 % 的窗 > 0.2 dB，压力格 2 s 平均中位只有 0.083 dB、> 0.2 dB 的时间 0.1 %。结果是低切整首开着、守护整首在收：平均 g 0.53 ～ 0.56，低切的改动量只剩 −4.0 ～ −4.5 dB（约 35 ～ 40 %）。
4. **同一现象在 22 首门槛歌里普遍存在**：自动低切最终开着的 5 首（emotapes、fule、somggggg、somggggg_mp3、woqu）守护全是 67 ～ 83 %、压力缩放全是 1；只有代价特别大的 WTF、will we be okay（P99 +1.2 / +1.9 dB）被压力反馈关到 0。
5. **与 T-043 是同一回路的两个口子**（见第 4 节）：顶峰真被抬的歌（somggggg、deep）漏在统计量稀释上；顶峰不抬、守护照样拉的歌（woqu、tech、fule、mp3）的伤害是 T-043 量到的「混合损失」（0 < g < 1 时最小相位低切与干路在 40 ～ 80 Hz 部分抵消，低音变小）。两条单独补都盖不全。修法归 T-043（先认领、已在改同一批文件，ADR-027），本线不并行改码，已发会话消息划界（第 5 节）。

6. **修复（同日 21:5x 起，Max 合入 PR #20 后回「好了」，按原任务书走 A）**：第一触发量改为与先试同口径——按有效音乐累计 100 ms 峰值块，
   整段 P99 比；两档证据（≥ 0.6 dB 满 10 s、0.2 ～ 0.6 dB 满 51.2 s）。门槛改前改后都 0 失败，216 行 204 行逐位相同；deep 低切关、守护

## 2. 守护模型（`tools/guard_model.py`）

照 `ClayModule.cpp` `PeakGuard::processBlock` 逐步写（E = 干路 ±8 ms 最大、P 1 s 包络、B = max(E, τP, F)、g_req、3 ms 前瞻最小、100 ms 线性释放、3 ms 滑动平均、10 ms 代价格），低切照 RBJ 两级高通（Q 同 ClayModule）。输入是原曲（插件里 Clay 前还有 Balance），不追求逐位。

核对：g < 1 占比 模型 71.23 % / 78.20 % ↔ 插件 70.89 % / 78.44 %；先试 20 Hz 候选在聆听窗口 [0, 14.6 s] 的 P99 代价 模型 +0.543 dB ↔ 分析器 +0.543 dB（deep）、−0.301 ↔ −0.301（tech）。
