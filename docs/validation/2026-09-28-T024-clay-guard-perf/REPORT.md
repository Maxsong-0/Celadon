## 2. 改了什么

只动 `Source/dsp/ClayModule.h` 的 `PeakGuard` 与 `ClayModule.cpp` 的守护一节，外加两处调用。
①～③、LinearPhaseLowpass、链都没动；CMakeLists / .jucer 的文件列表不用改。

| 项 | 改前 | 改后 |
|---|---|---|
| 调用方式 | 逐样本调用 `process (dry, wet, out)`，每样本搭 3 个小数组 | 每段（≤ 64 样本）调一次 `process (dry[], io[], 声道数, 样本数)`，状态在段内放局部变量、段尾写回 |
| 局部峰值 E（窗 2W + 1） | 逐样本单调队列；每样本 2 ～ 3 次整数取模；弹队尾的分支随数据走、常猜错 | 分段：最老样本所在段的后缀最大（段一完整就地算好）+ 中间完整段的最大（队列每段进一次）+ 当前段的前缀最大；每样本 3 次取大，没有随数据走向的分支 |
| 前瞻最小 h（窗 A + 1） | 逐样本单调队列（同上） | 同一套分段（与 E 共用段界），g_req 按样本号存进环，两条路都存 |
| g 路径 | 每样本全速 | 快路：见第 3 节 |
| 前瞻环 | 干路、处理后各两条 float 环 + 一条 uint8 标记环 | 一格放同一样本两声道的干路与处理后；标记环换成「最近一个处理后 ≠ 干路的样本号」 |
| 后缀最值 | — | 分 4 条独立的链算，不是一条 64 长的依赖链 |

- 浮点表达式原样保留，逐字相同：包络、界、g_req、代价格、释放、滑动平均、除法、输出混合。所以乘加融合与否的判断也一样
  （clang 默认 on，只合并同一表达式）。
- 单调队列容量取 2 的幂，下标按位与回绕；段长 S 取不超过 min(2W, A) 的最大 2 的幂、封顶 64。21.3 kHz 起都是 64；8 kHz 为 16、100 Hz 为 1。
- 声道数按调用方的来（`min(调用方, prepare 的)`）：修掉第 1 节那个越界。插件里走不到：处理器按输出声道数 prepare，进出声道数相同。
- 头文件里 `PeakGuard` 的注释、cpp 里守护一节开头的「实现」段写了上述理由。守护契约（ClayModule.h 文件头、ADR-014）一字未改。

## 3. 为什么逐位相同

- **分段滑动窗**：取大 / 取小是精确运算，结果与求值顺序无关。窗里仍是同一组数：E 为 [max(m − 2W, 0), m] 的干路量级，
  h 为 [max(m − A, 0), m] 的 g_req。所以值逐位相同。
  - 量级都是有限的 +0 或正数，g_req 在 [+0, 1]，没有 NaN，也没有 −0，所以不存在「同值取哪个」的差别。
  - S ≤ 窗长 − 1，保证最老样本所在的段在用到时已完整。
- **快路**：g 路径静止在全 1 指 releaseBelowOne == 0 且 released == 1。
  - 这时 r 的窗全是 1，releaseSum 已精确给成 A + 1。released == 1 说明上一个 h == 1，也就是当时窗里的 g_req 全是 1。
  - 再来一个 g_req == 1 的样本（没有声道 |y| > B），全速那一支的每一步都原地不动：
    - h 仍是 1；
    - r = min(1, 1 + 步长) = 1；
    - 释放环里 1 换 1，计数不变；
    - g 精确为 1，输出逐位 = y，统计不记。
  - 唯一变化是释放环的写位置前进一格，快路照做。
  - E、P、界、g_req 的环、代价格照常逐样本维护，所以任何时刻切回全速，状态都与一直全速跑的完全相同。**进出快路都不用重建任何状态。**
  - 「越界」只是原判据「x、y 有限且 |y| > B」的必要条件，越界就走全速那一支，由它按原判据细判。
- **isPassThrough**：「环里 G + 1 个样本有没有处理过的」等价于「最近一个处理过的样本号 ≥ 样本总数 − (G + 1)」。
  初值取 int64 最小，prepare 之前也与改前一样（对照工具专门比了这一点）。

## 6. 评估：还能怎么省，要不要继续

### 6.1 剩下的开销在哪（x86 剖析）

- 改后守护与 ①～③ + 低通大致各占一半：中性时守护 10.6 对 18.9，工作时 16.7 对 18.6（采样占比）。
- 守护里剩下的主要是固有的逐样本依赖链：包络 P = max(E, P·r) 与释放 r = min(h, r + 步长)，外加工作时的输出混合与 g = 和 / (A + 1) 的除法。
  除法不能换成乘倒数：换了就不逐位。实验把它换成乘法，也只省在噪声以内。

### 6.2 「按 64 样本段重写」

- 滑动窗这一块已经按段重写了（本次最大的一块收益）。
- 再往下是整段两遍式：先整段拷环、算量级，最后整段做输出混合，都可向量化。
  - 估计工作时守护再省 20 ～ 30 %，修坯一级约 8 ～ 12 %。
  - 要把前瞻环加长到 ≥ G + 64（段内写入不能覆盖还没输出的样本；isPassThrough 仍按 G + 1 算）。复杂度中等，对照工具可以原样复用。
- **建议**：先看 Mac 实测。新预算定下来以后若还差一点再做；否则不值得。

### 6.3 次要项：低通与守护每 65536 样本一次的精确重算尖峰（192k 约 1.5 µs）

- 论证过：**不能**在逐位不变的前提下分摊。
  - 重算是按环的下标顺序串行相加，环里下标小的那一段恰是最新写入的。
  - 浮点加法不满足结合律，所以这个和只能在重算时刻从头串行算，无法随时间边写边累加。
- 要分摊，就得改重算方式（例如按环回绕对齐、边写边累加）。低通输出会在舍入量级上变（约 1e-16 相对）：
  这需要先证明无害，再经 Max 同意。
- 影响：只有低通的重算那一块恰好撞上 Balance 的 FFT 那一块时（分频点切换后可能），192k / 32 那一块多约 1 pp。
- **建议**：这次不动；需要的话单开一条。

### 6.4 ①～③ 与低通（不在这次范围内）

- 可以省的地方：
  - 每样本的斜坡取值读的是成员，uint8 延迟标记的写入让编译器每样本重读；拷成局部量可以省掉；
  - 低通每样本一次跨文件调用，Linux 构建没有 LTO；
  - 低通可以改成整段批处理。
- 估计 ①～③ + 低通再省 20 ～ 30 %，修坯一级约 10 ～ 15 %。同样可以做到逐位不变，同样的对照工具可以验证。
