## 2. 先试后用的实现口径（关键取舍）

1. **候选**（各自单独作用在原始输入 L / R 上，系数公式照 ClayModule）：0 低切 = L、R 各两级 RBJ 高通（Q 用 ClayModule 的 `cutFirstQ / cutSecondQ` 同值），20 Hz；1～4 收单 = `LinearPhaseLowpass`（P1 的实现）a = 1，S' = S 延迟 D_c − LP(S)、M 延迟 D_c，D_c = `groupDelayFor(L_c)`；5 加宽 = S 过 2 kHz 高架（S = 1）+1.5 dB。块峰值：原始 max(|L|, |R|)，低切 max(|L'|, |R'|)，收单 / 加宽用 max(|M + x|, |M − x|) = |M| + |x|（浮点下也精确）。单声道输入：L = R，M = x、S = 0，低切只跑一路。
2. **块网格**：块 = round(0.1 s / 组长) 个**整组**（44.1 / 48 / 96 / 192 kHz 正好 100 ms；88.2 kHz 是 99.95 ms），从重启（`restartOnsets`）起算。**有效块** = 块里每个组都「过了重启预热、在学习区间内、在起音那份有效门上」（与真次声同一套边界），且块开始时候选已起跑满 250 ms（候选每次开始学习、每次重启都从零状态起跑，IIR 起跑瞬态要避开：20 Hz 那级振铃 τ ≈ 21 ms，250 ms 后 < −100 dB）。
3. **延迟补偿**：候选输出晚 D_c，它的第 k 块取输出的 [k·块长 + D_c, (k + 1)·块长 + D_c)，与原始第 k 块是同一段音频。这样纯单声道素材的收单代价**精确为 0**（任务书只要求 ≈ 0；不补偿时边界处的峰会落进相邻块，numpy：错开一块的对照素材上代价 −0.61 dB）。原始与 6 个候选都交齐才记下一块；D_c < 块长，所以任何时刻最多两块没交齐，2 个记录槽按块号奇偶轮用（写入顺序无关）。
4. **只在学习期间跑**：`runOnsets` 里 `learning` 为假时整段跳过（不耗 CPU）；开始学习 / 重启 / 坏样本后第一个学习中的样本前在音频线程上清零（`LinearPhaseLowpass::reset` ×4、延迟环 fill，不分配）。
5. **P99（与规格偏差，见第 3 节第 1 条）**：线性插值百分位（同 `numpy.percentile` 默认）。容量 512 块（51.2 s；maxListenSeconds 30 s ≈ 300 块 + 余量）；**满了之后不再记**（代价按前 512 个有效块算，注释写明）。每个序列只留最大的 8 个块峰值（有序插入），P99 与「存全部块峰值 + nth_element」逐位相同（n ≤ 512 时只用到第 7 大以内，`static_assert` 把关）。
6. **有效 / 置信度**：有效块时长 ≥ 10 s 才 valid；effectiveSeconds = 有效块时长；置信度 = min(有效块时长 / 10 s, 代表性)（valid 时即代表性）。代价 = 20·log10(P99 候选) − 20·log10(P99 原始)，候选 P99 按原始的 −120 dB 封底（不出 −∞）。每记下一块（至多每 100 ms 音频一次）重算，O(候选数)，没有尖峰。
7. **块长无关**：候选逐样本、块与组网格对齐、画像在记下新块的那一次 `processInput` 末尾更新——同一段音频任意切块逐位相同（测试覆盖 1 / 333 / 4096 / 随机）。我另在 numpy 里把 C++ 的记账（按组切段、倒数、记录槽、最大 8 值、插值）逐行移植，与「干净」的参照实现比对：512 / 333 / 1～4096 随机块长、学习起点不在块边界（5.013 s）、先送 5 s 再学习——块数与各代价**完全相同（差 0）**。

## 3. 与规格的偏差及理由

1. **P99 不存全部块峰值、不用 nth_element**（规格 3.2 与任务书写的是「固定容量数组 + std::nth_element 就地求」）。理由：每记一块要对 7 × 最多 512 个数做选择，约 10 µs 的单块尖峰；学习期在 192 kHz / 32 样本块下会进整插件「最坏块」验收（tools/perf 的 auto50 / auto100 场景是从新实例起跑，前 15～30 s 正在聆听）。改成每序列留最大 8 个值，数值与规格方法**逐位相同**，每块几十次比较。若主进程坚持规格写法，改回来只动 `countTrialWrite` / `percentileOfTop` 两处（加 7 × 512 的 double 数组与暂存）。建议回写规格措辞。
2. **块 = 整数个组**（规格「100 ms 块」）：为了与起音组同一套边界、块内组有效性可逐组判定；主流采样率正好 100 ms，88.2 kHz 99.95 ms。
3. **候选预热 250 ms**（规格没写）：候选只在学习期间跑、每次从零起跑，不避开起跑瞬态会把低切的阶跃响应算进块峰值。
4. **快路有效 = 平滑满自己的 120 ms**（规格「同重启规则」）：我理解为同一规则按各自时间常数；ClayGuard（P4 现有代码）在慢路无效时整路冻结、快路无效只是「没有加速证据」，两者兼容。
5. **高频两项（liveHigh*）在静音时仍冻结在最后的值与有效性**：规格 3.1 与 `ShortTermView` 冻结注释只要求两路低频相关度置无效，我没扩到高频（宽度保护的 V1-03 同类问题，见第 7 节第 6 条请主进程定）。

## 4. 不确定点

1. **性能**（未实测）：学习期每 512 样本块估计多 15～25 µs（每样本 4 次 `LinearPhaseLowpass::process` 的函数调用是大头，其余 5 个双二阶 + 延迟环 + 记账；步骤 2 把 4 个低通调用单独成环，免得冲掉第 3 步 IIR 状态的寄存器）；常态（不学习）只多真次声的 2 级双二阶，估计每块 +2 µs 左右。测试门槛见第 6 节。
2. **LinearPhaseLowpass 的重算尖峰**：4 个候选同时 reset，每 65536 样本在同一个样本上各做一次 O(4·L) 重算（192 kHz 下合计约 8000 次加法，一次约 2～3 µs），只在学习期；Clay 本身那一个也有。
3. **真歌上的有效块数**：有效块要求块内每个组都在起音那份有效门上；间歇很长的素材会少一些块。聆听满 15 s 时通常有 ≥ 14 s 有效块，不够 10 s 时代价无效 → P3 的决策按「没试过 → 该项中性」。
4. **候选设置固定**：低切 20 Hz、加宽 +1.5 dB 写死在分析器（它拿不到标定快照 `Constants`）。若以后标定改了风格低切目标上限或 `clayWidthMaxDb`，代价仍是按 20 Hz / 1.5 dB 量的（上界口径）。

## 5. 可能编不过的地方（已逐行自查，列出最没把握的）

- `std::array<BiquadCoefficients, subStageQ.size()>`：用命名空间级 `constexpr std::array` 的 `size()` 当模板实参（C++17 合法）。
- `static_assert` 里做 double 比较（`(1.0 − 0.99)·511 + 1 < 7`）。
- `configure`（noexcept）里的 `jassert`；`allocate()` 不带 noexcept（里面有分配），只在构造与 `prepare` 调。
- 测试：C++17 结构化绑定（性能护栏）、`juce::String (float)`、`std::array<std::array<float, 2>, 5>` 全括号初始化、模板 `makeKickTrain (…, Envelope&&)` 收 lambda、`std::make_pair (MusicProfile, AuxiliaryFeatures)`。
- `-Wshadow`：新代码里的局部名都避开了 `Impl` 的数据成员与 `juce::UnitTest` 的成员（没有 `name` / `fast` / `slow` / `window` / `profile` 等）；lambda 局部名不与外层局部重名。`-Wconversion`：所有 int / int64 / double / float 转换都显式。

## 7. 需要别的代理或主进程配合的地方

1. **主进程**：在服务器跑 `--only MusicAnalyzer,MusicAnalyzerClay`，看性能护栏日志里的两个均值（学习中估计 20～30 µs、不学习 6～8 µs）；如学习中逼近 60 µs，考虑第 8 条的接口。
2. **主进程 / P4（整链反相验收）**：慢路 + 快路 + ClayGuard 资格期后，整体反相的端到端时间估计约 **0.41 s**（48 k / 512：快路 < −0.2 约在切换后第 12 块、慢路 < 0.3 约第 14 块 ≈ 0.16 s，再加 0.15 s 资格期 + 0.1 s 攻击）。根治修订第 4 节第 2 条 (c)「从音频起 250 ms 内 a = 1」按这组常数做不到，需要主进程定：改验收口径，或调常数（例如快路门、资格期）。`ClayGlazeTests` 里按旧 60 ms 取小推的上限同样要改。
3. **主进程 / 各测试**：`subShareDb` 现在只认 < 16 Hz：20 Hz 正弦读数比以前低 15.6 dB、25～30 Hz 基本读不到。依赖「20 Hz 正弦触发低切」的整链测试（ClayGlaze 等）要换成 10 Hz 素材（根治修订第 4 节第 2 条 (d) 本来就是 10 Hz）。

7. **主进程**：规格 3.2 的「nth_element」措辞与第 3 节第 1 条的实现取舍，建议回写规格 / 实现计划。
