## 2. 实现要点与取舍

1. **位置**：只能在片 2——要两个声道都变换完。放在 `measureBandPowers()` 之后（单声道拷贝要用 `bandPower`）、`publishFrameSnapshot()` 之前（同一帧发布）。拆片关掉时三片在 hop 边界上接着做完，走的是同一段代码，两种做法发布的 `bandCross` 必然逐位相同。
2. **逐段直接读 bin，不建暂存**：`crossPowerOfBand` 按 `bandFirstBin / bandNumBins / bandWeightOffset / binWeights`（已含 `spectrumScale`），以与 `measureBandPowers` 相同的顺序与权重求段和，逐 bin 算 `reL·reR + imL·imR`（JUCE 交错布局 `buffer[2k] / buffer[2k+1]`，与 `accumulatePower` 同一读法）。只算 27 段覆盖的 bin（约 35 Hz～18 kHz：48 kHz 系 766 个、44.1 kHz 系 833 个，加 27 个边界 bin 重复），**与采样率无关**；比先算整条 `fftSize/2+1` 的交叉谱再求和省（192 kHz 时 4097 对 ≈ 800），也不需要在 prepare 里分配任何东西。估计每 hop 约 1 µs。
3. **只读由编译器保证**：交叉功率在 `const` 成员函数里算，经 `frameBuffer` 的 const 重载读 FFT 结果；`measureBandCross` 只写 `bandCross`。`frameBuffers` 之后还要被谐波保护读，这样它连被误改的可能都没有。
4. **口径**：`bandPower = Σw·(|X_L|² + |X_R|²)/2`（除以声道数），交叉功率本身不除，左右相同时两者相等。`float × float` 在 double 里精确，所以每个 bin 的交叉项与 `accumulatePower` 的 `re·re + im·im` 是同一种运算（只在相加时舍入一次，乘加融合与否结果都一样）——左右逐位相同时每个 bin 的两项逐位相同。
5. **单声道**：本帧分析声道数 `frameChannels < 2` 时 `bandCross = bandPower` 直接拷贝。用 `frameChannels` 而不是 prepare 时的 `numChannels`：立体声 prepare、宿主某块只送 1 个声道时，声道 1 的帧缓冲里是旧数据，绝不能用（测试 2 专门盖住）。
6. **多于 2 声道**：只取声道 0 / 1，不越界、只读本帧已变换的缓冲；此时与 `bandPower`（所有声道平均）口径不再严格对应——处理器只给 1 / 2 声道，写在注释里。
7. **钳位（规格未写，见第 4 节）**：先把非有限值归零（同 `bandPower`），再钳进 `[−bandPower, bandPower]`。
8. **CPU**：拆片的负担分布不变（192 kHz 最坏块来自约 22 µs 的 FFT，这里约 1 µs）。对 `BalancePerformanceTests` 的门槛估算：拆片最坏块比 0.51 → 约 0.52（门槛 0.65）；AArch64 立体声 / 单声道 1.14 → 约 1.18（门槛 1.4）；梳状素材 48k/512 均值 +约 0.01 个百分点。均为估算，未测。

## 3. 「G 与输出逐位不变」的论证

## 4. 与规格的偏差及理由

1. **钳位 `|bandCross| ≤ bandPower`**（规格没写）：精确运算下 `|X| ≤ P` 恒成立（逐 bin `2·Re(L·R*) ≤ |L|² + |R|²`，权重非负），越界只来自两边段内求和的舍入（左右相同 / 相反时 1e-16 量级）。不钳的话，纯单声道素材上 `P_S = (P − X)/2` 可能是 −1e-16·P，读者一旦对它取 `log10` 就是 NaN。钳住后快照里（double → float 舍入单调、对称）`P_M、P_S ≥ 0`、`ρ ∈ [−1, 1]` 严格成立。写进了头文件的文件头说明。
2. **每 hop 开销**：规格估「约 1000 次」，实际约 800 次（段只到 18 kHz）。
3. **测试放在新测试类 `BalanceCrossPower`**，没有塞进 `BalanceTests::runTest`：遵守「已有测试文件只在末尾追加」（加进 `runTest` 要改中间行）。全套运行（`runTestsInCategory ("Celadon")`）自动包含；定向跑用 `--only BalanceModule,BalanceCrossPower`。先例：`DspPartsTests.cpp` 一个文件三个类。

## 6. 自查：可能编不过的地方

逐行按 `-Wall -Wextra -Wshadow -Wconversion -Wno-sign-conversion` 核过，结论：未发现问题。重点核对项：

- 声明与定义签名一致：`const float* frameBuffer (int) const noexcept`、`void measureBandCross() noexcept`、`double crossPowerOfBand (size_t) const noexcept`。const 重载不改变已有调用的解析（调用处都在非 const 成员函数里，仍选非 const 版）。
- `juce::jlimit (-bandPower[b], bandPower[b], cross)` 三个都是 double；`bandPower ≥ 0`，jlimit 里的 `jassert (lower <= upper)` 不会触发。
- 类型转换全部显式；沿用本文件的 C 风格写法 `(double) / (float) / (size_t)`（全文件如此，C 风格转换同样是显式转换，`-Wconversion` 不报）。
- 遮蔽：局部名避开了测试文件命名空间级常量（`numChannels / maxBlock / hopAt48k / numBands / bandOf1kHz`）、`juce::UnitTest` 的成员（`name / category / runner`）和 .cpp 匿名命名空间里的常量。
- 测试用到的 JUCE 接口已在 `../JUCE`（9.0.2）源码核对：`String::toHexString (IntegerType)`（`juce::uint64` 走 `createHex (uint64)`）、三参数 `jmax`、`String (double, int, bool)`。
- 新辅助都有用到（无 `-Wunused-function`）；聚合初始化字段写全（无 `-Wmissing-field-initializers`）；无有符号 / 无符号比较。

## 7. 不确定点

1. 统计门槛与 M/S 重建容差是解析推导的，没有跑数值模拟核对（本机不跑），已留 ≥ 7σ / 100 倍余量。
2. 「R 取负 → G 逐位不变」依赖 FFT 引擎对输入取负严格对称：vDSP 与 JUCE 回退引擎都只做线性运算（信号 × 常数旋转因子、加减），IEEE 就近舍入对称，逐值成立；若将来换成有数据相关分支的引擎，这条可能误报（与本改动无关）。
3. 每 hop 约 1 µs、各性能门槛的影响是估算。
4. 测试类放法（新类而非塞进 `BalanceTests::runTest`）是按「只在末尾追加」理解的，如主进程希望合并进 BalanceModule 类，只需把 6 个用例搬进去并在 `runTest` 里调用。
