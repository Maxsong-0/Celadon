## 2. 关键设计取舍

1. **旧存档按「旧字段白名单」造，不猜新字段名**：用本版本 `toXml` 写出，再按 v0.1.6.2 的字段表只留旧属性、formatVersion 一律写回 1、删掉旧版本没有的子节点。新字段叫什么（A5 / A6 的选择）不影响夹具；反过来若新版本改了任何旧属性名，夹具断言 `missingLegacyAttributes == 0` 会直接指出（旧工程会读不回来）。画像先降成格式 1 再算画像号，校准参考条件与执行快照里的画像号跟着改，所以是一份自洽的旧存档。
2. **旧工程「与全关逐位相同」用不带校准与执行快照的旧存档比**：A6 把 Clay 三态并进 `manualParamsHash`（默认设置与 v0.1.6.2 逐位相同，「全关」不同）。若旧存档带着有效校准 / 执行快照，它们只对「抽屉默认」那条链适用、对「全关」不适用，两条链的 Limit Gain 会因此不同——那不是 Clay 的差别。所以逐位对照用校准无效、无执行快照的旧存档（两条链都没有依赖哈希的已存状态，之后的校准轮两边逐位同步）；「校准照旧适用」另在带校准的真实旧存档上单独断言。
3. **GLAZE 0 直接对照「改动前」的链**：除「默认 / 全关 / Bypass 三者逐位相同」外，再与自己串起来的 Balance → Color → Limit（交同样的手动值、同样先 set 后 prepare、每块先 set 再按序 process）逐位对照——这正是 v0.1.6.2 的 CeladonChain 在 GLAZE 0 时对样本做的全部事（已核对 A7 的新链：同一块参数契约、Listen 关时不碰样本）。手动值开成「各模块都在工作」，让比较有分量。
4. **反相保护的时序从音频起算，并把 300 ms 平滑的过零时间做小**：冻结接口看不到「实时相关度过阈值」那一刻，只能从插入反相音频起量。反相段功率按实测做成正常段 40～125 Hz 的 25 倍，一阶 300 ms 平滑下 X̃ 过零只要约 12 ms（按一半比例从严折算 25 ms），上限写成「攻击 0.1 s + 分析窗 2048 + hop 512 + 发布偏移 64 样本 + 5 ms 斜坡 + 过零 + 4 块粒度」≈ 228 ms。按 A6 当前代码（保护在 beginBlock 用上一块的视图与秒数更新）推算实际约 160～180 ms。
5. **实时 / 离线要求逐样本相同**（rendercheck「realtime/offline audio matches exactly」、规格「逐样本一致」），比任务书的「响度差在容差内」更严；64 与 1024 块长之间才用响度容差。60 s 渲染从同一份已锁定、已校准、Clay 三项都 > 0 的存档起步（「Clay 生效时」写成夹具断言），锁步比较、不存整段输出（省内存）。
6. **执行快照在「保护介入中」存**：攻击完成后再过 0.1 s（仍在反相段里，保护值稳定在 1），首块比较不受「保护每块推进一步」的影响；另外核对 EXECUTION 里确有 `clayGuard.phaseActive / phaseFloor` 与 `liveClay`，并续渲到保护退回——证明保护值没被当成方案存死。
7. **阳性对照**：每个「不变 / 中性」断言都配一个「会变」的对照（手动低切、格式 2 画像、自动态保护、默认抽屉的超低频能量等），见第 5 节。

## 3. 与规格 / 任务书的偏差及理由

1. **用例 4 的攻击时限**：任务书「100 ms（+ 一个分析帧与块的滞后）」；我的上限另含 300 ms 功率平滑的过零时间（≈ 25 ms，靠 25 倍功率比压小）、5 ms 淡入斜坡、4 块粒度，合计 ≈ 228 ms。理由：规格 1.4 规定实时相关度是 300 ms 平滑后相除，第 3 节「攻击 ≤ 100 ms」只能从「视图判定反相」起算；同响度反相从插入起算约 0.3 s（A2 报告第 4 节第 1 条已提请主进程裁决）。若主进程裁定「从插入起 100 ms」，需要 A4 给反相检测更短的平滑，届时把本用例的 `effectiveRatio` 与块数收紧即可。
2. **用例 2 的相关度频段取 40～125 Hz**（任务书写「< 125 Hz」）：素材里 20 Hz 超低频是同相的，自动低切会削掉它、反而拉低 < 40 Hz 的相关度；40～125 Hz 正是分析器 `lowCorrelation` 的频段，只反映收单的作用。
3. **用例 6 另加整体响度差 < 0.02 LU**（任务书只要求 3 s 窗）；rendercheck 原门限是窗 0.2 LU / 整体 0.1 LU，实测 0.0137 / 0.0073 / 0 LU。
4. **用例 5 的「< 20 Hz 能量」用 15 Hz 测试音 + 4 阶 20 Hz 低通量**：解析值 −24.1 dB（4 阶 Butterworth 30 Hz 高通在 15 Hz），门限 −18 dB；另加「默认抽屉与输入相差 < 0.1 dB」「200 Hz 以上相差 < 0.05 dB」两条。
5. **用例 3 额外断言旧校准照旧适用、拧 GLAZE 后仍中性、重新聆听后启用、全关时不提示**：来自实现计划关键约定「computeProfileId 对格式 1 画像结果不变（校准不失效）」、规格第 7 节「点『重新聆听』后启用」、`Status::clayNeedsRelearn` 定义「有自动态的项」。

## 6. 可能编不过的地方（逐行自查后）

未发现确定的问题。按 `-Wall -Wextra -Wshadow -Wconversion -Wno-sign-conversion`（clang 与 GCC）核过的低风险点：

- 全部数值转换显式 `static_cast`；int64 / size_t / int / float / double 之间没有隐式收窄；`std::sin (float)` 走 float 重载。
- `-Wshadow`：命名空间常数用 `k` 前缀；各用例里的 `s` 都在互不嵌套的作用域；lambda 体内的局部名（`s`、`st`、`executedClay`）都不与外层局部同名（GCC 对 lambda 更严，逐个核对过）；没用 `name` / `category` / `runner` 等 juce::UnitTest 成员名；局部名没用 `small` / `large`（Windows 宏）。
- JUCE：`String (const char*)` 在 Debug 下断言 ASCII——所有字符串字面量已脚本核对为纯 ASCII；`StringArray` 用 `return { … }` 走 `initializer_list<const char*>` 构造；`XmlElement::removeAttribute` 的 String → Identifier 隐式转换、`setAttribute (…, int)`、`removeChildElement (…, true)` 签名已对照 JUCE 9 头文件。
- `std::size` 需要 `<iterator>`（已包含）；`static constexpr std::int64_t` 成员（C++17 隐式 inline）。
- 所有匿名命名空间函数与 `ClayRig` 成员都有调用（`-Wunused-function`）；没有未用参数 / 变量 / lambda 捕获。
